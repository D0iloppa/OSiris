## 0. 이 문서가 존재하는 이유

같은 부류의 실수가 세 번 반복됐다. 매번 워커가 "설치 시점에 미리 셋팅"했고, 매번 사용자가 정정했다.

| # | 사건 | 무엇을 미리 했는가 | 사용자의 정정 |
|---|---|---|---|
| 1 | 프로바이더 API 키 | `.env`에 `ANTHROPIC_API_KEY`를 두고 부트스트랩이 omniroute로 자동 밀어넣음 | "그 API 키 관리하는 역할을 하려고 omniroute를 도입하는 건데 어불성설임." |
| 2 | 공개 도메인 | `gw/conf.d/default.conf`에 `server_name osiris.example.com`를 고정 | "server_name 같은 것들 아직 지정할 수 없어야 해. 나는 내 사이트에 구성하는 게 아니라 프레임워크를 만드는 거야." |
| 3 | omniroute 관리자 비밀번호 | 설치 시점에 무작위 생성해 `.env`에 저장, compose가 `:?`로 그 값 없이는 기동조차 거부 | (같은 원칙의 재발 지적 — §9.5의 시크릿 판정표로 정정) |

세 사건 모두 **사후에** 발견되고 개별적으로 고쳐졌다. 매번 고친 워커가 "이번엔 다르니 예외적으로"가 아니라 "이건 저번과 같은 부류다"라고 스스로 판단할 수 있는 **일반 기준**이 없었기 때문에 세 번 반복됐다. 이 문서의 목적은 그 기준을 한 번 세우고, 향후 네 번째 사건이 생기기 전에(사후 발견이 아니라 사전 판정으로) 걸러내는 것이다.

## 1. 판정 기준

### 1.1 이미 있던 기준 — 시크릿 축 (계승)

`10-core-architecture.md` §9.5(I5 2차·3차 수정)가 시크릿에 대해 이미 확정한 기준:

> **"이 값을 사람이 화면에서 직접 보거나 입력하는가?" — 그렇다면 온보딩 소관(설치 스크립트가 미리 만들지 않는다). 아니라면(순수 기계 간 인증) 설치 시점 자동 생성 + `.env`가 정당하다.**

이 기준은 사건 1·3을 정확히 걸러낸다(프로바이더 키·omniroute 관리자 비밀번호는 둘 다 "사람이 화면에서 직접 보는" 값이었다). 그러나 이 기준은 **시크릿에만** 적용되도록 좁게 쓰여 있다 — 사건 2(공개 도메인)는 시크릿이 아니므로 이 기준만으로는 걸러지지 않았다.

### 1.2 일반화 — 시크릿을 넘어 전체 설정값으로

**판정 기준의 최종 형태 (한 문장)**:

> **이 값이 "조직의 의도"(누가·무엇을·어떻게·어디로)를 표현하는가, 아니면 "이 스택이 어디에 배포되든 항상 참인 배선 사실"인가 — 전자면 온보딩 소관이고 후자면 설치 시점 결정이 정당하다. 자격증명에는 그 위에 "사람이 화면에서 직접 보거나 입력하는가"라는 하위 기준을 겹쳐 적용하고, 조직 의도이지만 조직이 아직 존재하지 않는 시점에 값이 필요한 경우(예: LLM 게이트웨이 배선)에는 프레임워크가 잠정 기본값을 제시하고 온보딩이 확인·수정하게 하는 완충 지대(프레임워크 기본값)를 둔다.**

이 한 문장이 3분류(§2 이하 표의 열 이름)의 정의이기도 하다:

| 분류 | 정의 | 전형적 신호 |
|---|---|---|
| **설치 시점 결정 가능** | 조직 의도와 무관한 순수 배선 사실. 어느 배포에서도 값의 *존재*는 필수지만 값의 *내용*은 조직을 몰라도 결정된다 | 서브넷 CIDR, 컨테이너 이름, 내부 서비스 DNS 이름, 기계 간 인증 |
| **온보딩이 결정** | 조직의 의도를 표현하거나, 조직이 실재하는 사람의 판단(도메인 소유, 예산, 프로바이더 선택)을 필요로 한다 | 팀/직무/사람/에이전트, 공개 도메인, 프로바이더 자격증명 |
| **프레임워크 기본값(온보딩이 제시)** | 온보딩이 결정할 항목이지만, 조직이 존재하기 전에도 스택이 부팅되려면 잠정값이 있어야 한다. 코드는 이 값을 *적용*하지 않고 *제시*만 한다 | `omniroute/config.json`의 별칭→모델 매핑, `PUBLIC_ORIGIN=http://localhost:$PORT`, 기본 `PermissionProfile` 3종 |

### 1.3 결정 절차 (신규 설정값 도입 시 따라갈 질문 순서)

새 설정값을 추가하려는 워커는 아래 순서로 질문하고, 처음으로 "예"가 나온 질문의 답을 분류로 채택한다. 이 순서는 §0의 세 사건을 실제로 걸러내도록 구성했다(§1.4에서 검증).

```
Q1. 이 값이 없으면 스택이 기동조차 못 하는가?
    (compose의 ${VAR:?...} 처럼 값이 없으면 하드 실패)
      │
      ├─ 예 → 즉시 재검토 대상이다. "기동 필수"를 관대한 기본값/옵셔널
      │        구성으로 낮출 수 있는가?
      │          ├─ 낮출 수 있다 → 낮춰라. ${VAR:-} 옵셔널로 바꾸고
      │          │   그 기능이 빈 값에서도 정상 기동하게 만든다(사건 3의
      │          │   정정 방식). 이후 Q2로 계속 진행해 최종 분류를 정한다.
      │          └─ 낮출 수 없다(정말 이 값 없인 스택 정의 자체가 안 됨,
      │              예: NEO4J_AUTH 없인 Neo4j 컨테이너가 시작 인자를
      │              못 받음) → 설치 시점 결정. 단, 이런 경우는 매우
      │              드물어야 한다 — 대부분의 "필수처럼 보이는 값"은
      │              사실 옵셔널 기본값으로 낮출 수 있다(사건 3 참고).
      │
      └─ 아니오 → Q2로.

Q2. 이 값을 사람이 화면(콘솔/omniroute UI 등)에서 직접 보거나 입력하는가?
      │
      ├─ 예 → Q2a. 그 값을 판단하려면 "조직"이 존재해야 하는가, 아니면
      │         조직과 무관한 호스트/운영자 개인 설정인가(예: 이 서버가
      │         죽었을 때 누구에게 알릴지)?
      │           ├─ 조직 무관(호스트/운영자 설정) → 부트스트랩 대화형
      │           │   입력(온보딩 아님, 그러나 자동 생성도 아님 — 그
      │           │   자리에서 사람에게 직접 물어본다). §2.2 watchdog 참고.
      │           └─ 조직에 관한 것 또는 조직의 LLM/외부 스택 배선에
      │               관한 것 → 계속 Q2b로(저장하기 전에 교환 경로를 먼저
      │               확인한다 — 사건 4가 이 확인을 건너뛴 결과다).
      │
      │   Q2b. (신규, 사건 4로 추가) 이 값을 반복 사용하려면 저장이
      │        필요한데 — **저장해야 하는 것이 사람의 원본 자격증명 그
      │        자체인가, 아니면 그 원본을 스코프 제한된 기계 자격증명으로
      │        교환할 수 있는 경로가 있는가**(예: 비밀번호 로그인 API와는
      │        별개로, 그 로그인 세션 안에서 발급 가능한 API 키/토큰
      │        엔드포인트가 이미 존재하는가)?
      │           ├─ 교환 경로가 있다 → **원본은 절대 저장하지 않는다.**
      │           │   교환을 1회 수행하고, 그 결과물(키/토큰)만 저장한다.
      │           │   그 결과물은 "사람이 보는 값"이 아니므로 Q2를 다시
      │           │   타면 **아니오**가 되어 Q3 이하의 일반 규칙(순수 기계
      │           │   간 인증 취급)을 그대로 받는다 — 별도 규칙이 아니라
      │           │   Q2 재귀일 뿐이다.
      │           └─ 교환 경로가 없다(또는 확인되지 않았다) → **온보딩이
      │               결정**하되, 원본을 저장할지는 §2.2의 판정표에 사례를
      │               추가해 명시적으로 근거를 남긴다(침묵한 채로 저장하지
      │               않는다 — 저장하기로 했다면 왜 교환 경로가 없다고
      │               판단했는지 한 줄을 남긴다, 이것이 사건 4의 교훈이다).
      │
      └─ 아니오(순수 기계 간 인증) → Q3.

Q3. 이 값이 그래프(팀/직무/사람/에이전트/역량/배정정책)의 일부이거나
    그로부터만 파생되는가?
      │
      ├─ 예 → **온보딩이 결정**(20-ontology-schema.md §9의 시드 순서를 탄다).
      │
      └─ 아니오 → Q4.

Q4. 이 값이 "이 프레임워크가 어디서든 배포될 수 있다"는 성질과 충돌하는
    사이트별 사실인가(공개 도메인, 상위 게이트웨이 유무, TLS 종단 위치,
    특정 브랜드/도메인 문자열)?
      │
      ├─ 예 → **온보딩이 결정.** 설치 스크립트는 로컬호스트/빈 값 기본만
      │        둔다(사건 2의 정정 방식 — `server_name _;`, `DEV_NET_NAME=`
      │        비움).
      │
      └─ 아니오 → Q5.

Q5. 이 값이 순수 배선(내부 서비스 이름, 서브넷, 포트, 이미지 태그)이며
    조직이 존재하든 안 하든 항상 같은가?
      │
      ├─ 예 → **설치 시점 결정 가능.**
      │
      └─ 아니오 → Q6.

Q6. 이 값의 "이름/구조"는 설계가 고정하지만 "내용"은 대표의 확인을
    필요로 하는가(예: 별칭 이름은 3개로 고정이지만 각 별칭이 가리킬
    모델은 확인이 필요)?
      │
      ├─ 예 → **프레임워크 기본값(온보딩이 제시).** 코드는 이 값을
      │        적용하지 않고 `getDefaultAliasMapping()`류의 읽기 전용
      │        함수로 제시만 한다.
      │
      └─ 아니오 → 애매한 경우다. **프레임워크 기본값**으로 두고(가장
                   안전한 중간 지대), 이 문서 §5의 태그 스키마로
                   `[미검증]` 표시해 다음 워커가 재검토하게 한다.
```

### 1.4 네 사건을 이 절차로 재확인

| 사건 | Q1 | Q2 | Q2a/Q2b | 결과 | 실제로 걸러지는가 |
|---|---|---|---|---|---|
| 1. 프로바이더 키 | 아니오(값 없어도 부팅됨, `PUT`은 나중) | **예** | Q2a: 조직의 LLM 배선에 관한 것 | 온보딩이 결정 | ✅ |
| 2. `server_name osiris.example.com` | 아니오 | 아니오(사람이 값을 "입력"하는 지점이 아니라 코드가 박아넣은 문자열) | — | Q4에서 **예**(사이트별 사실) → 온보딩이 결정 | ✅ |
| 3. omniroute 관리자 비밀번호(설치 스크립트가 구운 것) | **예**(`:?`로 강제) → 재검토: 낮출 수 있다(`INITIAL_PASSWORD:-`로 옵셔널화, 미설정 시 omniroute 자신의 첫 접속 화면이 대신함) | 이후 Q2 재적용 → **예**(사람이 화면에서 직접 입력) | Q2a: 조직에 관한 것(누가 이 게이트웨이 대시보드를 볼 수 있는가) | 온보딩(또는 하위 시스템의 자체 온보딩)이 결정 | ✅ |
| **4. omniroute 관리자 비밀번호(온보딩이 `.env`에 저장하려 한 것) — 신규, 이 감사 도중 발생·정정** | 아니오 | **예**(사람이 직접 입력) | Q2a: "공유 인프라 관리 자격증명"이라는 세 번째 범주 → 그럼에도 저장 여부를 정하기 전에 **Q2b를 거치지 않았다**(당시엔 Q2b가 없었다) → "그럼 `.env`에 저장"으로 곧장 건너뜀 | **틀림 — 사건 3과 같은 값을 다시 저장** | ❌(이 절차 v1으로는 못 걸러짐 — 그래서 v1에 있던 것) |

**사건 4가 중요한 이유**: 이건 다른 세 사건과 다르다 — **이 판정 기준을 만든 문서 자신이 그 기준을 어겼다.** §1.1~§1.2가 "사람이 화면에서 직접 보거나 입력하는가?"를 자격증명 축의 하위 기준으로 세워 두고도, 그 기준이 "예"로 나온 뒤에는 "그러니 저장한다"로 곧장 건너뛰었다 — **저장 외에 다른 선택지(교환)가 있는지 확인하는 절차가 없었다.** 감독이 omniroute 소스(`requireManagementAuth.ts`)를 실측해 관리 API가 `manage` 스코프 API 키 인증을 대시보드 쿠키와 동등하게 받는다는 사실을 확인시켜 주었고(§2.2/§2.3에 실측 결과 반영), 이 발견이 **Q2b**를 낳았다. 절차가 스스로의 결함을 실측으로 드러내고 다음 판을 낳은 사례로 남긴다 — 이 문서도 완결된 규범이 아니라 계속 반증 가능해야 한다는 것을 보여주는 가장 좋은 증거다.

세 사건 모두 Q1~Q4 안에서 걸러진다 — 이 절차가 사후 대응이 아니라 사전 판정으로 같은 결론에 도달함을 확인했다.

### 2.5 축 E — 프레임워크 기본값(default)의 성격

이 축은 다른 네 축에 걸쳐 나타나는 **패턴**이므로 별도 항목 목록이 아니라 그 패턴 자체를 규정한다.

**정의**: 온보딩이 최종 결정할 항목이지만, 조직이 존재하기 전에도 값이 있어야 한다(스택이 부팅되거나, 온보딩 UI 자신이 그 값을 "제시"할 대상이 필요하다). 코드는 이 값을 **적용하지 않고 제시만** 한다 — `getDefaultAliasMapping()`처럼 읽기 전용으로 노출하는 함수가 이 패턴의 정규 형태다.

**"설치 시점 결정"과의 차이**: 설치 시점 결정은 "이 값은 조직과 무관하다"이고, 프레임워크 기본값은 "이 값은 조직에 관한 것이지만 지금은 잠정값을 보여줄 뿐이다"이다. 혼동하면 사건 2류의 실수가 재발한다 — `PUBLIC_ORIGIN=http://localhost:18280`을 "이건 어차피 기본값이니 설치 시점에 정해도 된다"고 착각하면, 다음 워커가 이 값을 도메인처럼 코드에 다시 박아 넣을 위험이 있다. **판별 질문**: "이 기본값을 온보딩 UI가 보여주고 사람이 확인/수정하는 화면이 (계획상이라도) 있는가?" 있으면 프레임워크 기본값, 없으면(그 값이 그냥 거기 있고 아무도 안 보여줄 계획이면) 설치 시점 결정으로 재분류해야 한다.

**현재 이 저장소의 실태**: 온보딩 UI/`osiris-api`가 아직 구현되지 않았으므로, 프레임워크 기본값 항목들은 전부 "보여줄 계획은 있으나 아직 아무도 안 보여주는" 상태다. 이것은 설계 위반이 아니라 순서상의 미구현이다 — `omniroute/operations.mjs`의 `getDefaultAliasMapping()`이 이미 이 계약을 코드로 준비해 두었고(§9.6 인계), `PUBLIC_ORIGIN`도 주석으로 "온보딩이 갱신한다"고 명시되어 있다(§1.1의 판정 절차가 실제로 통과하는지는 온보딩 UI가 만들어질 때 재확인이 필요 — `[미검증]`).

### 3.3 경계선 사례 — `OSIRIS_MAX_RESIDENT_AGENTS`

**현재 상태**: `.env.example`에 `OSIRIS_MAX_RESIDENT_AGENTS=4`(주석: "사용자 확정: 상주 에이전트 최대 4명"). `orchestrator/internal/reconcile/reconcile.go`가 이 값을 신규 에이전트 admission의 하드 상한으로 쓴다(코드 확인 — 이미 실행 중인 에이전트는 유지되고, 신규 admission만 거부).

**긴장의 근원**: `10-core-architecture.md` §1.4/§1.5/40-console-ia.md Ops 화면은 "좌석 환산"을 **동적으로 계산**(직무별 `RoleResourceProfile` × 실제 호스트 CPU/RAM)해서 "이 정도면 개발자 에이전트 몇 명을 더 앉힐 수 있는가"로 보여줘야 한다고 명시한다(G10: "좌석/용량을 프론트에 하드코딩하지 않는다. `RoleResourceProfile`에서 백엔드 계산"). 그런데 실제 구현은 리소스 계산이 아니라 **개수 상한 하나**를 정적으로 둔다.

**판정**: 이것은 사건 2류의 명백한 위반은 **아니다** — G10이 금지하는 것은 "프론트에 하드코딩"이고 이 값은 백엔드(orchestrator) 코드에 있으며, 코드 주석도 "seat count is always computed here, in code, from `OSIRIS_MAX_RESIDENT_AGENTS` — never hardcoded in a frontend"라고 그 경계를 의식하고 있다. 또한 실제 리소스 기반 좌석 계산 자체가 아직 구현되지 않은 상태에서, 개수 상한은 합리적인 1단계 안전판(safety valve)이다.

**그럼에도 `[갭]`으로 남기는 이유**: 값 "4"가 어디서 왔는지가 문서화되어 있지 않다 — 이 개발 호스트의 실측 사양(§1.5 core-architecture: "8GiB/4vCPU면 4~6명이 현실적 상한")에서 온 값인지, 프레임워크 보편 기본값으로 의도된 것인지 구분되지 않는다. §1.2의 "프레임워크(어디서든 배포)"라는 원칙을 이 값에도 적용하면, 호스트 사양을 실측하지 않고 고정된 "4"를 모든 배포의 기본값으로 남기는 것은 사건 2(특정 호스트의 사실을 프레임워크 기본값으로 오인)와 **같은 모양의 위험**을 안고 있다 — 다만 대가가 훨씬 작다(도메인처럼 기동 실패를 유발하지 않고, 단지 신규 admission을 과도하게/느슨하게 거부할 뿐이다).

**권고 (구현하지 않음, 다음 워커 인계)**: 좌석 환산(리소스 기반 동적 계산)이 구현되면 이 정적 상한은 "하드 세이프티 실링"(호스트가 뻗는 것을 막는 최후 방어선, 넉넉하게 설정)으로 역할을 좁히고, 실제 admission 판단은 계산된 좌석 수가 맡아야 한다. 그 전까지는 `.env.example`의 주석에 "이 값은 이 개발 호스트의 실측 사양에서 나온 예시이며, 실제 배포에서는 호스트 사양에 맞춰 조정할 것 — 향후 좌석 계산 구현 시 이 변수의 역할이 좁아질 예정"이라는 문구를 추가하는 것으로 충분하다(코드 변경 없이 오분류 위험만 낮춤).

## 4. 신규 설정값 도입 결정 절차 — 요약

§1.3의 플로차트가 정본이다. 워커가 실무에서 쓸 체크리스트 형태로 요약하면:

1. **이 값이 없으면 스택이 기동을 거부하는가?** 그렇다면 먼저 그 요구 자체를 낮출 수 있는지 검토한다(옵셔널 기본값 + 그 기능의 성능 저하 허용). 사건 3이 이 패턴이다.
2. **사람이 화면에서 이 값을 직접 보거나 입력하는가?** 그렇다면, 그 판단이 "조직"을 전제하는지 "이 호스트를 운영하는 사람 개인"을 전제하는지 구분한다. 전자는 온보딩, 후자는 부트스트랩 대화형 입력.
3. **이 값이 그래프(조직)의 일부이거나 그로부터 파생되는가?** 그렇다면 온보딩(정확히는 `20-ontology-schema.md` §9의 시드 순서).
4. **이 값이 도메인/상위 게이트웨이/TLS처럼 "이 프레임워크가 특정 사이트에 묶여 있다"는 인상을 주는 사이트별 사실인가?** 그렇다면 온보딩이 결정, 설치 스크립트는 로컬호스트/빈 값 기본만.
5. **위 넷 다 아니고 순수 배선(내부 DNS, CIDR, 포트, 이미지 태그)인가?** 그렇다면 설치 시점 결정.
6. **이름/구조는 설계가 고정하되 내용은 확인이 필요한가?**(별칭 이름은 고정, 모델 매핑은 확인 필요) 그렇다면 프레임워크 기본값 — 코드는 제시만 하고 적용하지 않는다.
7. 그래도 애매하면 프레임워크 기본값으로 두고 `[미검증]` 태그를 남긴다.

**핵심 재확인 질문(사건 3 재발 방지 전용)**: "이 값을 몰라도 `docker compose up -d`가 전 서비스 healthy로 끝나는가?" 답이 "아니오"라면 그 자체가 재검토 신호다 — 프레임워크는 "설치하면 즉시 로컬호스트에서 뭔가가 뜨고, 그다음 온보딩"이 되어야 한다(IMPLEMENTATION-NOTES I5 §56).

## 5. 위반 감지 방법 (명세만 — 구현은 다음 워커)

문서만으로는 또 반복된다. 이 저장소에는 이미 같은 종류의 회귀를 실제로 잡은 린트 선례가 둘 있다 — `bin/lint-driver-boundary.sh`(Docker API 타입이 `driver/docker` 밖으로 유출되지 않는지 검사, G3), `bin/lint-health-invariant.sh`(헬스 핸들러가 금지된 락/자식 프로세스 의존을 갖지 않는지 검사, §5.4). 같은 패턴 — "설계 문서의 규칙을 grep/파싱 가능한 불변식으로 좁혀서 CI가 자동으로 검사"를 이 경계에도 적용한다.

### 5.1 `.env.example` 태그 커버리지 검사 — `bin/lint-onboarding-boundary.sh`(신설, 명세만)

**요구하는 표기 스키마**: `.env.example`의 모든 `KEY=VALUE` 줄(주석·빈 줄 제외) 바로 위 주석 블록 안에 아래 태그 중 정확히 하나가 있어야 한다.

```
# osiris:boundary=install-time            (축 무관 순수 배선, §2.1/§2.5 "설치 시점 결정 가능")
# osiris:boundary=onboarding              (조직 의도 또는 사이트별 사실, "온보딩이 결정")
# osiris:boundary=framework-default       ("프레임워크 기본값(온보딩이 제시)")
# osiris:boundary=machine-secret          (자격증명, 기계 간 인증, 사람 미대면)
# osiris:boundary=human-facing-secret     (자격증명, 사람이 화면에서 직접 보거나 입력 — 온보딩/하위시스템 소관)
```

**검사 내용**:
1. 태그가 없는 `KEY=` 줄이 있으면 실패(어떤 축에도 배정되지 않은 값 — 이 감사가 잡으려는 정확히 그 결함).
2. `human-facing-secret` 태그가 붙은 변수의 `.env.example` 기본값이 **비어 있지 않으면** 실패(사건 1·3 재발 — 사람 대면 값을 설치 스크립트가 미리 채움).
3. `machine-secret` 태그가 붙은 변수는 기본값이 `CHANGE_ME*` placeholder이거나 비어 있어야 한다(랜덤 생성 안내 주석 존재 여부를 grep).
4. `.env.example`에 새 줄이 추가되는 PR/커밋에서 이 스크립트가 실패하면 병합을 막는다(CI 훅) — 지금 두 린트와 동일한 강제 지점.

### 5.2 compose 하드 실패(`:?`) 금지 린트 — 사건 3 재발 감지

**검사**: `docker-compose*.yml` 전체에서 `${[A-Z_]+:\?` 패턴(bash 파라미터 확장의 `:?`, 필수 강제)을 grep. 매치가 있으면 실패하고 매치된 변수명을 출력.

**예외 처리**: 정말 필수인 값(§1.3 Q1에서 "낮출 수 없다"로 판정된 극히 드문 경우)은 `# osiris:boundary-exception: <근거 한 줄>` 주석을 그 서비스 정의 바로 위에 요구하고, 그 주석이 있으면 해당 줄만 통과시킨다(예외를 완전히 금지하지 않고 "말해야 하는 예외"로 만든다 — 침묵하는 하드 실패를 없애는 것이 목적이다).

### 5.3 도메인/사이트 리터럴 금지 린트 — 사건 2 재발 감지

**검사**: `gw/conf.d/*.conf`, `docker-compose*.yml`, `orchestrator/**/*.go`, `core/**` (구현되면)에서 `server_name` 뒤에 `_` 또는 변수가 아닌 리터럴 도메인 패턴(`[a-z0-9-]+\.[a-z]{2,}`)이 오면 실패. 이미 `server_name _;`이므로 현재는 PASS 상태이며, 이 린트는 **회귀 감지용**(다음 워커가 실측 편의를 위해 다시 박아넣는 것을 막는다).

### 5.4 프로바이더 시크릿 리터럴 금지 린트 — 사건 1 재발 감지

**검사**: 추적 대상 파일 전체(`.env.example`, `omniroute/*.mjs`, `docker-compose*.yml`, `docs/**`의 예시 코드 블록 제외)에서 `ANTHROPIC_API_KEY=`(값이 비어있지 않은 것), `apiKeyEnv`, 또는 `sk-ant-`/`sk-proj-` 형태의 리터럴 키 패턴을 grep. 매치가 있으면 실패. IMPLEMENTATION-NOTES §59가 이미 수동으로 이 grep을 1회 수행했다 — 이를 반복 가능한 스크립트로 고정하는 것이 이 항목의 전부다.

### 5.5 `human-facing-secret` 값의 코드 내 영속화 금지 린트 — 사건 4 재발 감지 (신규)

**이 사건은 §5.1~§5.4의 검사로는 못 잡힌다는 것을 자백해야 한다.** 사건 4에서 `OSIRIS_OMNIROUTE_ADMIN_PASSWORD`의 `.env.example` 기본값은 **처음부터 비어 있었다**(§5.1 규칙 2를 이미 통과) — 문제는 정적 파일이 아니라 **설계·코드가 그 값을 런타임에 `.env`로 써넣으려 했다는 것**이었다. `.env.example`만 보는 린트로는 이 종류의 결함이 원천적으로 안 보인다.

**검사**: `.env.example`에서 `human-facing-secret` 태그가 붙은 변수명 목록을 추출한 뒤, 그 변수명 각각에 대해 `omniroute/*.mjs`·(구현되면) `osiris-api/**`·`bin/*.sh` 전체를 grep해 그 변수명을 인자로 받아 파일에 쓰는 함수 호출(`writeFileSync`/`appendFileSync`/`applyGatewayTokenToEnv`류 헬퍼에 그 변수명이 전달되는 패턴)이 있으면 실패. 즉 **"사람 대면 값을 파일에 쓰는 코드가 존재하는가"**를 코드베이스 전체에서 확인한다 — `.env.example`이 아니라 `.mjs`/`.go`/`.sh` 소스가 검사 대상이라는 점이 §5.1~§5.4와 다르다.

**이 린트가 통과하려면**: 사건 4의 정정처럼, human-facing-secret은 오직 **교환 오퍼레이션의 인자**로만 등장해야 하고(예: `exchangeAdminPasswordForManageKey({password})`), 그 함수의 반환값(교환 산출물, machine-secret 태그가 붙을 값)만 파일에 쓰여야 한다. 검사 스크립트는 "교환 함수 인자로 등장하는 것"과 "파일 쓰기 함수 인자로 등장하는 것"을 구분해야 하므로 순수 정규식보다는 AST 기반 검사가 더 안전하다 — 정규식으로 시작해도 되지만(1단계 Simplicity First), false negative 가능성을 이 명세에 정직하게 남긴다.

### 5.6 신규 항목 인계 체크 (프로세스, 코드 아님)

`.env.example`에 새 변수가 추가되는 모든 PR/커밋은 §5.1의 태그가 있어야 통과하므로 **자동으로** 이 문서의 §1.3 절차를 거치게 강제된다. 이것이 "문서만으로는 또 반복된다"는 문제에 대한 실질적 답이다 — 사람이 이 문서를 읽었는지에 의존하지 않고, CI가 태그 부재를 실패로 만든다.

## 7. 이 문서가 앞으로 하는 일

이 문서는 `.env.example`이 바뀔 때마다 다시 감사되어야 하는 **살아있는 판정표**다. §5.1의 린트가 구현되면 이 문서의 §2·§3 표는 그 린트의 "설계 근거"(태그가 왜 저 값을 가져야 하는지의 설명)로 남고, 실제 최신 상태 확인은 린트 통과 여부로 대체된다 — 표가 코드와 따로 노는 것을 막는 것이 §5의 존재 이유다.
