> 범위: **능력 스택(capability stack)이라는 일반 개념**의 정의·수명주기·해석 계약, 설치 시점과 온보딩 시점의 분리 문제와 그 해소, 그 해소가 넓히는 신뢰 경계의 봉쇄, 두 개의 실사례(메일 / SCM·CI), 도메인 없는 설치, 온보딩 8단계의 정의와 현 구현 상태.

>
> **표기 규칙**: 표기 없는 서술 = 이 문서의 확정 결정. `[미검증]` = 공식 출처나 실측으로 확인하지 못한 가정. `[갭]` = 현재 어떤 문서·코드에도 답이 없는 공백. `[실측]` = 이 작업에서 코드/매니페스트를 직접 읽어 확인한 사실.

## 0. 결정 요약 (S1~S15)

| # | 결정 | 한 줄 근거 | 대가 |
|---|---|---|---|
| S1 | **능력 스택**을 1급 개념으로 세운다: 선택적으로 프로비저닝되는 스택 하나가 **능력 키(capability key) 집합**을 공급하고, 기능은 스택이 아니라 **키**에 의존한다 | 메일은 첫 사례일 뿐이다. SCM/CI가 두 번째이고, 세 번째(결제·전화·문서서명 등)가 올 때 매번 새 배선을 발명하지 않으려면 지금 일반화해야 한다 | 개념이 하나 늘고, 기능이 키를 조회하는 간접층이 하나 생긴다 |
| S2 | 스택의 **부재는 오직 그 키에 의존하는 기능만** 비활성화한다. 다른 어떤 판정·경로·화면도 바꾸지 않는다 | 사용자 확정: "설치는 DNS 도메인 없이도 성공해야 한다". 부재가 전역으로 번지면 그 문장이 거짓이 된다 | 모든 소비 지점이 부재 경로를 실제로 갖고 있어야 한다(테스트 부담) |
| S3 | 스택 내부의 구현 선택(자가호스팅 MTA인가 외부 SMTP 릴레이인가)은 **경계 위에서 관찰 불가능**하다 — 상위 계층은 키의 해석 결과만 본다 | 사용자 확정: "다른 계층에서는 관심사 밖" | 두 모드의 능력 집합이 다를 때 그 차이를 **모드가 아니라 키로** 표현해야 한다(§4.2 — 이것이 릴레이 모드에서 수신이 성립하지 않는 문제의 정직한 해법이다) |
| S4 | 능력 해석은 **`osiris-core`가 유일한 결정자**이고 3상태(`available` / `degraded` / `unavailable`)이며 **미지의 키는 `unavailable`**(fail-closed) | 2상태로 하면 "기능이 없음"과 "지금 고장남"이 구분되지 않아 소비 측이 큐잉·재시도 여부를 결정할 수 없다 | 소비 측이 3상태를 다 다뤄야 한다. §2.3에서 계약으로 고정 |
| S5 | **온보딩은 스택 CR을 직접 만들지 않는다.** 온보딩은 그래프에 **선언(`:CapabilityStackDecl`)** 을 쓰고, 오퍼레이터가 그 선언을 읽어 CR과 워크로드로 수렴시킨다 — 에이전트가 `:AIAgent` 노드에서 Pod로 수렴되는 것과 **완전히 같은 모양** | K9/D1을 그대로 재사용한다. 새 권한이 `osiris-core`에 붙지 않는다(core는 여전히 그래프만 쓴다, `70` §7.1의 구분 유지) | 선언과 물성 사이에 비동기 지연이 생긴다 — 커밋은 인프라를 기다리지 않는다(그리고 그것이 이득이다, §3.4) |
| S6 | 스택 CR의 spec에는 **PodSpec·image·command·args·env가 존재하지 않는다.** 스택 종류는 차트에 실린 **닫힌 카탈로그**이고 CR은 그 카탈로그 항목의 **파라미터만** 나른다. CRD 스키마에 `additionalProperties: false` | "오퍼레이터가 임의 인프라를 만들 수 있게 됐다"를 **표현 불가능**하게 만든다. 규약이 아니라 API 서버가 거부한다 | 새 스택 종류를 더하려면 차트/이미지를 갱신해야 한다 — 런타임 확장성을 의도적으로 포기한다 |
| S7 | 스택 워크로드는 **`osiris-stacks` 전용 네임스페이스**에 두고, **별도 ServiceAccount `osiris-stack-operator` + 별도 Deployment**가 수렴시킨다. 기존 `osiris-orchestrator` SA에 권한을 얹지 않는다 | `[실측]` 현재 orchestrator SA는 `osiris-agents`에 5종 리소스 + Agent CR, `osiris-system`에는 leases/events **뿐**이다(`deploy/osiris/templates/rbac-operator.yaml`). 그 좁음이 자산이므로 깨지 않는다. 같은 파드에 두 루프를 넣으면 토큰이 하나라 권한이 합쳐진다 — 분리는 **프로세스가 분리될 때만 실재**한다 | 파드 하나·Deployment 하나가 늘어난다. 이미지는 같은 것을 서브커맨드로 쓰므로 빌드 비용은 0 |
| S8 | 스택 선언을 쓸 수 있는 주체는 **`org.admin`(또는 신설 `org.manage.stacks`)을 가진 `:Person` 세션뿐.** `:AIAgent`는 구조적으로 불가 | 정의 평면/실행 평면 분리(`80-action-layer.md` D1). 에이전트가 인프라를 소환할 수 있으면 프롬프트 인젝션 한 방이 클러스터 변경이 된다 | 자동 복구(에이전트가 스스로 스택을 다시 세움)를 포기한다 |
| S9 | **DNS 도메인은 `:Organization`의 선택 필드**(`dnsDomain`, `mailDomain`)로 신설한다. 없으면 없는 채로 조직이 성립한다 | `[실측]` 현재 `:Organization`은 `id/name/legalName/timezone`뿐이고(`20` §3.1, `core/internal/graphdb/seed.go:seedOrganization`) 도메인 개념이 아예 없다 | `20-ontology-schema.md`에 스키마 델타가 필요하다(§10에 제안으로 남긴다 — 이 문서는 그 파일을 고치지 않는다) |
| S10 | OSiris는 **DNS 레코드를 조회·대조·표시만** 한다. DNS 프로바이더 API 자격증명을 **받지 않는다** | 사용자 확정: 도메인 전체를 다시 쓸 수 있는 자격증명을 보유하지 않는다. `31` §1.3 Q2b의 논리와 같다 — 교환해서 스코프를 좁힐 경로가 없는 원본 자격증명은 애초에 들이지 않는다 | 레코드 생성은 사람의 수작업이고, 그 사이 스택은 `degraded`로 머문다 |
| S11 | **메일 스택은 `stk.mail.send`와 `stk.mail.receive`를 별개 키로 공급한다.** 릴레이 모드는 send만 공급할 수 있다 | 정직한 실패: "외부 SMTP 릴레이"는 발신 전용 프로토콜이다. 수신은 MX + 사서함(또는 프로바이더 inbound 웹훅)을 요구한다. S3(모드 불가시성)을 지키면서 이 비대칭을 표현하는 유일한 방법은 **키를 쪼개는 것**이다 | 소비 측이 "메일 스택이 있는가"가 아니라 "이 키가 있는가"를 물어야 한다 — 그것이 애초에 S1의 요구다 |
| S12 | 수신 메일은 **`:InboundMessage`(불변 출처 기록)** 가 되고, `:WorkItem`은 그로부터 **파생될 수 있을 뿐 자동으로 되지 않는다.** 스택은 본문을 해석하지 않는다 | 외부 메시지가 곧바로 실행 가능한 업무가 되면 신뢰 경계가 메일 서버까지 밀려난다. 승격 판정은 액션 계층(D1)의 몫 | 인바운드 → 업무 전환에 사람 또는 정책 게이트가 낀다(그것이 목적) |
| S13 | **진입 경로(콘솔 호스트명·Ingress·TLS)도 능력 스택**이다(`stk.ingress.public`). 차트의 `ingress.host`는 부트스트랩 폴백이고 권위는 그래프 선언이다 | `[실측]` `values.yaml`의 `ingress.host`/`tlsSecretName`은 기본이 빈 문자열이며 이미 "도메인 없는 설치"를 전제한다. 온보딩이 도메인을 정하는데 그 값이 `helm install` 시점에 고정되어 있으면 §3의 문제가 여기서 그대로 재현된다 | 스택 오퍼레이터가 `osiris-system`의 **Ingress 1개(resourceNames 고정)** 를 다룰 권한을 갖는다 — 워크로드 생성 권한이 아님을 §3.5에서 명문화 |
| S14 | 온보딩 **커밋의 호출자는 사람의 세션**이다(1회차 = master-key 세션, 2회차+ = `org.admin` 세션). 커밋 요청은 **`expectedRevision` 선행조건**을 실어 재시도 안전하게 만든다 | F14는 genesis 주체에서 commit을 제거했을 뿐 **다른 문을 정의하지 않았다** — 그 공백이 "커밋 엔드포인트가 아예 없다"로 굳었다(`[실측]` 코드베이스에 `POST /onboarding/commit` 부재). 이 결정은 F14를 뒤집지 않고 **그 반대편 문을 명세한다** | 최초 커밋은 `:Party` 없는 세션이 mutating 요청을 보내는 유일한 경우다 — `60` §6.5의 술어를 좁게 명확화해야 한다(§7.6) |
| S15 | 0단계에 **egress 허용목록 수렴**을 정식 단계(0-2b)로 넣고, 성공 판정에 "등록된 모든 프로바이더의 도메인이 실행 중인 squid 설정에 존재"를 추가한다. 도메인은 **프로바이더→도메인 고정표**에서만 나온다(자유 입력 불가) | `31` §2.3의 egress 갭(사용자 지시의 `31 §202`)을 닫는다. 자유 입력을 허용하면 온보딩 폼이 곧 방화벽 우회 도구가 된다 | 프로바이더 고정표에 없는 신규 프로바이더는 차트 갱신 없이 못 쓴다 — S6과 같은 성질의 의도적 제약 |

### 1.2 중복 금지 규칙

이 문서가 다른 문서의 결정을 **다시 적는 유일한 경우**는 인용부호를 붙여 원문을 인용할 때다. 그 외에는 §번호로 가리키기만 한다. 특히:

- **프롬프트 인젝션·오염 전파·액션 승인 게이트는 한 줄도 규정하지 않는다.** §4.5는 메일 스택이 **부착해야 할 필드 목록**만 정하고, 그 필드로 무엇을 판정할지는 D1의 몫이다.
- **에이전트 Pod 생성 로직은 규정하지 않는다.** `10` §1.4 / `70` §5가 소유한다.
- **omniroute 오퍼레이션 계약은 규정하지 않는다.** `30` §1.0.4가 소유한다.

## 2. 능력 스택 모델

### 2.1 정의

> **능력 스택**은 (a) 선택적으로 프로비저닝되고, (b) 프로비저닝되면 하나 이상의 **능력 키**를 공급하며, (c) 프로비저닝되지 않으면 **그 키에 의존하는 기능만** 사용 불가가 되고 시스템의 다른 어떤 부분도 영향받지 않는, 자기완결적 배선 단위다.

세 조건 중 **(c)가 정의의 핵심**이다. (a)(b)만 만족하는 것은 그냥 "선택적 컴포넌트"이고, 그런 것은 이미 여럿 있다(`50-integration-adapters.md`의 Plane/텔레그램 어댑터). 능력 스택이 새 개념인 이유는 **부재가 국소적이라는 것을 계약으로 강제**하기 때문이다.

**용어 충돌 경고 — 반드시 읽을 것.** `20-ontology-schema.md` §5는 이미 **역량(`:Capability`, `cap.*`)** 을 "사람/에이전트가 보유한 숙련"의 뜻으로 쓴다. 이 문서의 **능력 키**는 완전히 다른 것이다 — "이 설치에 이 기능이 존재하는가"이지 "누가 잘하는가"가 아니다. 두 개념이 섞이면 배정 알고리즘(`20` §8)의 하드 필터가 오염된다. 따라서:

| | `:Capability` (기존) | 능력 키 (신규) |
|---|---|---|
| 접두 | `cap.` | **`stk.`** |
| 의미 | 주체(`:Party`)의 숙련 | 설치(installation)의 기능 가용성 |
| 보유자 | `:Person` / `:AIAgent` | 없음 — 설치 전체의 성질 |
| 소비처 | 배정 하드 필터·점수(§8) | `:ActionType.requiresCapability`(D1), 콘솔 표면 |
| 레벨 | 1~5 척도 | 없음 — 3상태만 |

**`cap.`과 `stk.`는 절대 같은 이름공간에 들어가지 않는다**(CS1).

### 2.2 수명주기

```
       (선언 없음)
            │  org.admin 세션이 :CapabilityStackDecl 을 커밋
            ▼
       ┌──────────┐  스택 오퍼레이터가 선언을 관측
       │ declared │──────────────┐
       └────┬─────┘              │ 선행조건 미충족(DNS 미전파, 시크릿 부재,
            │ 수렴 시작            │ 의존 스택 부재…) → 수렴을 시도조차 못 함
            ▼                     ▼
      ┌─────────────┐      ┌───────────┐
      │ provisioned │      │ blocked   │  ← reason 필수. 사람이 할 일이 화면에 뜬다
      └──────┬──────┘      └─────┬─────┘
             │ 스택 자체 헬스 통과       │ 조건 충족
             ▼                     │
       ┌──────────┐◀───────────────┘
       │ healthy  │──── 헬스 실패/부분 실패 ────▶┌──────────┐
       └────┬─────┘◀──── 회복 ──────────────────│ degraded │
            │                                   └──────────┘
            │ org.admin 세션이 선언을 close (삭제가 아니라 closedAtRevision)
            ▼
       ┌──────────┐
       │ removed  │  CR 삭제 → ownerReference GC. 그래프 선언은 남는다(P4)
       └──────────┘
```

**상태별 키 해석**(이것이 §2.3 계약의 근거다):

| 스택 상태 | 그 스택이 공급하는 키의 해석 | 왜 |
|---|---|---|
| 선언 없음 / `removed` | `unavailable` | 기능이 이 설치에 존재하지 않는다 |
| `declared` / `blocked` | `unavailable` (+ `reason`) | 아직 존재하지 않는다. 소비 측은 "없음"과 똑같이 다뤄야 한다 — "곧 생길 것"에 기대어 큐잉하면 무한 큐가 생긴다 |
| `provisioned` | `unavailable` | 워크로드는 떴지만 헬스가 아직 통과하지 않았다. 낙관하지 않는다 |
| `healthy` | `available` | |
| `degraded` | **`degraded`** | 존재는 하는데 지금 못 쓴다. **큐잉이 허용되는 유일한 상태**(단, 아래 단서를 반드시 읽을 것) |

**`degraded`가 왜 별도 상태여야 하는가**: 발신 큐를 예로 들면 — `unavailable`이면 큐에 넣는 것 자체가 잘못이다(영영 나가지 않는다). `degraded`면 큐에 넣는 것이 맞다(MTA가 곧 돌아온다). 2상태로 뭉개면 두 경우 중 하나가 반드시 틀린다. 이것은 `10` §1.5가 "완화라고 적지 않은 항목은 실제로 포기하는 것"이라고 한 것과 같은 정직성 요구다.

> **`[2026-08-12 정밀화]` "소비 측의 재량"이 어디까지인가 — 액션 계층의 독법이 정본이다.**
>
> 이 절의 초판은 `degraded`를 "소비 측이 재시도/큐잉을 **선택할 수 있는** 상태"로 서술했다. 그 산문을 자연스럽게 읽으면 "소비 측이 `degraded`를 가용으로 쳐도 된다"로 읽히는데, **그 독법은 금지된다.** `80-action-layer.md` §5.4.1(AD14)이 확정한 좁은 독법이 정본이다:
>
> - **가용성 판정에서 `degraded`는 `unavailable`과 동일하다.** 가용성 술어는 `∀k: state(k) == 'available'`이며, `degraded`인 키를 요구하는 액션은 카탈로그에서 `disabled`이고 호출되면 `409 CAPABILITY_UNAVAILABLE`이다.
> - **재량은 가용성 판정 뒤에만 있다.** 이미 모든 게이트를 통과해 **사람의 승인을 받은** 집행 요청이 집행 직전에 열화를 만났을 때, `osiris-core`가 그것을 지연 큐에 적재하는 것 — 그 하나뿐이다. `unavailable`에서는 큐잉 자체가 금지된다(위 표 `declared`/`blocked` 행의 "무한 큐" 논거와 같은 이유).
>
> **왜 좁혀야 하는가**: 열화 진입 조건(릴레이 레이트리밋, 업스트림 5xx, DNS 흔들기)은 전부 **외부에서 자극 가능**하다. 능력 상태가 어떤 축의 엄격도든 낮출 수 있게 두면 공격자가 열화를 유도해 게이트를 낮출 수 있다 — 유도된 열화가 곧 게이트 우회가 된다. 따라서 능력 상태가 할 수 있는 일은 **차단과 지연뿐**이며 둘 다 안전한 방향이다.
>
> 그럼에도 3상태를 2상태로 뭉개지 않는 이유는 그대로다 — 거부 응답의 `state` 필드와 **큐 적격 여부**에서 두 상태는 끝까지 구별되므로, 이 절이 `degraded`를 만든 목적은 가용성 게이트 **뒤에서** 온전히 보존된다.

### 2.3 ★ 존재/부재 해석 계약 (D1이 이것에 맞춰 설계 중 — 정밀하게 읽을 것)

`80-action-layer.md`의 `:ActionType.requiresCapability`가 소비할 계약을 여기서 **완전히** 고정한다. 이 절의 C-1~C-11은 구현이 아니라 **약속**이다.

#### C-1. 키 문법 (고정)

```
stk.<stack>.<facet>[.<sub>]      소문자, 숫자, 마침표, 하이픈만. 최대 64자.
예: stk.mail.send · stk.mail.receive · stk.mail.address.per-party
    stk.scm.repo.read · stk.scm.repo.write · stk.scm.webhook
    stk.scm.credential.rotate · stk.ci.run
    stk.ingress.public · stk.ingress.tls
```

정규식: `^stk\.[a-z0-9-]+(\.[a-z0-9-]+){1,2}$`. 이 정규식을 만족하지 않는 문자열은 키가 아니며, 키가 아닌 것을 `requiresCapability`에 넣는 것은 **정의 시점 오류**다(CS4).

> **`[2026-08-12 정정]` 대문자 금지는 예시에도 적용된다.** 이 문서의 초판은 사서함 키를 `stk.mail.address.perParty`로 적었는데, 그 문자열은 **위 정규식을 만족하지 않는다**(`[a-z0-9-]`에 대문자 `P`가 없다). 즉 이 문서가 스스로 규정한 CS4에 자기 예시가 걸리는 상태였다. `stk.mail.address.per-party`로 정정했다(두 문서 7곳 전부). 다단어 facet은 **하이픈**으로 잇는다 — camelCase는 키 문법이 아니다.

> **`[2026-08-12 추가]` `stk.scm.credential.rotate`.** `80` §4.6의 `secret.rotate` 액션이 요구할 키가 초판 레지스트리에 없었다(`80` G-A1로 회신됨). C-2가 "키는 선택이지 발명이 아니다"라고, CS4가 미지 키를 정의 시점 하드 오류로 못박았으므로 `80`이 이름을 지어낼 수 없었다 — 레지스트리를 소유한 이 문서가 채운다. 공급 주체는 SCM 스택이며(§5), 회전 대상은 그 스택이 보관하는 자격증명(PAT·웹훅 시크릿)이다. **LLM 프로바이더 키 회전은 이 키의 범위가 아니다** — OmniRoute는 능력 스택이 아니라 필수 구성요소이고(§1), 그 키 관리는 온보딩 0단계와 `79` §6의 소관이다.

#### C-2. 키 레지스트리는 닫혀 있다

전체 키 목록은 **차트/이미지에 실린 정적 레지스트리** 하나에서만 나온다(스택 카탈로그의 부산물, S6). 런타임에 키가 발명되지 않는다. LLM은 키를 **선택**할 수 있을 뿐 **발명**할 수 없다 — `30` O3("역량/권한의 선택이지 발명이 아니다")과 같은 규율이다.

#### C-3. 해석기는 하나다

```
GET  /v1/capabilities            → 전량 스냅샷
GET  /v1/capabilities/{key}      → 단건
```

`osiris-core`가 소유한다. `osiris-api`·콘솔·오퍼레이터·에이전트 중 **누구도 스택의 헬스를 직접 보고 스스로 판정하지 않는다**(D17이 그래프 쓰기에 대해 요구한 단일 관문과 같은 이유: 판정이 두 벌이면 반드시 어긋난다).

#### C-4. 응답 형상 (고정)

```jsonc
{
  "key":        "stk.mail.send",
  "state":      "available" | "degraded" | "unavailable",   // 정확히 3개. 확장 금지
  "stackId":    "stack-mail" | null,     // unavailable(미선언)이면 null
  "mode":       null,                    // ★ 항상 null. §2.4 참조 — 절대 모드를 노출하지 않는다
  "reason":     "MX_NOT_RESOLVING",      // available이면 null, 그 외는 필수(기계 판독 코드)
  "reasonText": "…",                     // 사람용. 인가 판정에 쓰지 말 것
  "since":      "2026-08-12T04:11:02Z",  // 이 state가 된 시각
  "observedAt": "2026-08-12T04:22:31Z"   // ★ 필수. P2 — 관측값은 observedAt 없이 존재할 수 없다
}
```

#### C-5. 미지의 키는 오류가 아니라 `unavailable`이다 (fail-closed)

레지스트리에 없는 키를 조회하면 404가 아니라 `{"state":"unavailable","reason":"UNKNOWN_KEY"}`를 반환한다. **404를 반환하면 소비 측의 오류 처리 경로와 부재 경로가 갈라지고, 그 둘 중 하나는 반드시 테스트되지 않는다.** 한편 정의 시점(`:ActionType` 생성)에는 미지의 키가 **하드 오류**다(CS4) — 런타임은 관대하고 정의 시점은 엄격하다.

#### C-6. 판정과 실행은 다르다

`available`은 **사전조건**이지 **실행 성공 보증이 아니다**. 소비 측은 다음을 전제해야 한다:

- 판정 시점에 `available`이었어도 실행이 실패할 수 있다.
- 실행 실패는 능력 해석의 문제가 아니라 액션의 문제다 — 능력을 다시 묻지 말고 액션 오류로 다뤄라.
- 하나의 액션 판정은 **하나의 스냅샷**으로 평가한다. 한 판정 안에서 같은 키를 두 번 조회해 다른 답을 얻는 일이 없어야 한다(CS6).

#### C-7. 캐시와 신선도

`osiris-core`는 해석 결과를 **최대 15초** 캐시할 수 있다. 응답의 `observedAt`이 그 신선도를 드러낸다. 소비 측이 자체 캐시를 두는 것은 **금지**한다 — 두 번째 캐시가 생기는 순간 "왜 콘솔은 되는데 에이전트는 안 되는가"류의 진단 불가능한 상태가 생긴다(CS7).

#### C-8. 부재는 부재만 일으킨다

`unavailable`이 유발할 수 있는 것은 정확히 두 가지다: (i) 해당 키를 요구하는 `:ActionType`의 거부, (ii) 그 액션에 대응하는 콘솔 표면의 비활성/숨김. **그 외 어떤 것도 바꾸지 않는다** — 로그인, 배정, 승인, 프로비저닝, 헬스, 다른 스택의 상태 어느 것도 영향받지 않는다(CS2). 이것이 S2를 계약 수준으로 못박은 문장이다.

#### C-9. 거부의 형상

키가 부족해 액션이 거부될 때의 오류는 다른 인가 실패와 **구분 가능**해야 한다:

```jsonc
{ "error": "CAPABILITY_UNAVAILABLE",
  "key": "stk.mail.send", "state": "unavailable", "reason": "NOT_DECLARED" }
```

권한 부족(403 `PERMISSION_DENIED`)과 능력 부재(409 `CAPABILITY_UNAVAILABLE`)를 같은 코드로 뭉개면, 관리자가 "권한을 더 주면 되겠지"라고 잘못된 조치를 한다. **HTTP 상태는 409를 쓴다** — 403은 "당신이 못 한다"이고 409는 "이 설치가 못 한다"이다.

#### C-10. 관측 가능성

키 해석의 상태 전이는 전부 `capability.<key>.<state>` 이벤트로 NATS에 발행된다. 콘솔은 이 이벤트로 실시간 갱신하고 폴링하지 않는다(D19/D20의 SSE 경로 재사용, 새 경로를 만들지 않는다).

#### C-11. 이 계약이 **약속하지 않는 것** (D1이 기대하면 안 되는 것)

- **어떤 스택이 그 키를 공급하는지에 대한 안정성**: `stackId`는 진단용이며, 같은 키가 다른 스택으로 옮겨갈 수 있다.
- **모드/구현 정보**: `mode`는 영구히 `null`이다(§2.4).
- **미래 상태**: "곧 healthy가 된다"는 정보는 제공하지 않는다. `blocked`의 `reason`은 사람에게 할 일을 알려주기 위한 것이지 자동화가 대기하라는 신호가 아니다.
- **트랜잭션성**: 능력 해석은 그래프 트랜잭션에 참여하지 않는다. 커밋 도중 능력이 바뀌어도 커밋은 영향받지 않는다.

### 2.4 왜 `mode`를 절대 노출하지 않는가

사용자의 문장을 그대로 계약으로 만든 것이다 — 메일이 자가호스팅인지 외부 릴레이인지는 **스택 내부 사정**이고 "다른 계층에서는 관심사 밖"이다. 기술적 근거를 덧붙이면:

1. **한 번 새면 되돌릴 수 없다.** `mode`가 응답에 있으면 6개월 뒤 어딘가에 `if (mode === 'selfhosted')`가 생기고, 그 순간 S3은 문서에만 남는다. `10` §1.7의 G1~G10이 전부 같은 형태의 예방 조치다.
2. **모드는 능력의 대리변수로 부정확하다.** 릴레이 모드라고 반드시 수신이 없는 것이 아니다(프로바이더 inbound 웹훅 방식이 있다). 능력을 알고 싶으면 **능력을 물어야** 한다 — 그것이 S11이 키를 쪼갠 이유다.
3. **콘솔의 운영 화면은 예외가 아니다.** 관리자가 "지금 무슨 모드인가"를 봐야 한다면 그것은 `GET /v1/capabilities`가 아니라 **스택 관리 화면**(`GET /v1/stacks/{id}`, `org.admin` 전용)에서 본다. 두 표면을 분리하는 것이 계약을 지키면서 운영 정보를 주는 방법이다.

### 2.5 스택 간 의존

스택이 다른 스택의 키를 요구할 수 있다(예: `stk.scm.webhook` ← `stk.ingress.public`). 규칙:

- 의존은 **키 단위**이지 스택 단위가 아니다(CS8).
- 의존 키가 `unavailable`이면 의존하는 스택은 `blocked`(수렴 시도 안 함)이며, **부분 공급은 허용된다** — SCM 스택은 웹훅 없이도 `stk.scm.repo.read/write`를 공급할 수 있다. 즉 **스택 하나가 공급하는 키들이 서로 다른 상태를 가질 수 있다**(CS9). 이것이 "스택 단위 on/off"보다 키 단위 모델이 우월한 실증이다.
- 의존 사이클은 정의 시점 오류(CS10). 레지스트리가 정적이므로 차트 빌드 시점에 검사 가능하다.

## 3. 설치 시점과 온보딩 시점의 분리

### 3.1 문제

```
helm install         ← 이 순간 values.yaml이 고정된다
     │
     ▼
클러스터 기동 (코어만 존재, 조직 없음, :OrgRevision{n:0})
     │
     ▼
사람이 콘솔을 열고 온보딩 대화를 한다     ← 메일 스택이 필요한지 여기서 정해진다
     │
     ▼
"메일 스택을 쓰겠다"                     ← 그런데 helm values는 이미 굳었다
```

`31-onboarding-boundary.md`가 세 번 반복된 사건으로 확립한 원칙은 "조직 의도는 설치 시점에 굽지 않는다"였다. 그 원칙을 지키면 **필연적으로** 이 문제가 생긴다 — 조직 의도가 설치 이후에 결정되는데, 인프라를 만드는 수단(Helm)은 설치 시점에만 작동하기 때문이다.

세 가지 오답과 왜 오답인가:

| 안 | 내용 | 판정 |
|---|---|---|
| (a) `helm upgrade --set mail.enabled=true`를 온보딩이 실행 | 가장 직관적 | **기각.** ① 온보딩 백엔드가 클러스터 전체를 재수렴시킬 권한(=사실상 cluster-admin)을 갖게 된다 — `10` §1.4가 compose 재생성안을 기각한 것과 **같은 이유**(무관한 서비스 재시작 + 권한 과대). ② values가 진실의 두 번째 소유자가 되어 D1 위반. ③ 실행 중인 에이전트 턴을 끊을 수 있다 |
| (b) 모든 스택을 항상 설치하고 비활성 상태로 둔다 | 설치 시점 결정으로 되돌리기 | **기각.** 자가호스팅 MTA를 "안 쓸 수도 있는데 항상 띄운다"는 것은 루프백 설치의 자원 전제를 깬다. `10` §1.4의 (c) 슬롯 풀 기각과 같은 형태 |
| (c) 사람이 나중에 수동으로 `helm upgrade` | 정직하지만 | **기각.** `31` §2.1이 `DEV_NET_NAME`에 대해 이미 이것을 **[갭]** 으로 판정했다("온보딩 UI/API가 이를 대신 수행하는 엔드포인트가 없다"). 같은 갭을 새로 하나 더 만드는 셈 |

### 3.2 해소 — K9의 모양을 그대로 재사용한다

에이전트는 이미 같은 문제를 풀어 두었다. `70` K9/K5의 흐름:

```
온보딩이 그래프에 :AIAgent 를 쓴다  →  orchestrator가 그래프에서 파생  →  Agent CR  →  Pod+PVC+SA+Secret+NetworkPolicy
        (의도)                                                          (물성)                    (실행)
```

스택은 **같은 흐름의 다른 인스턴스**다:

```
온보딩이 그래프에 :CapabilityStackDecl 을 쓴다  →  stack-operator가 파생  →  CapabilityStack CR  →  카탈로그가 정한 오브젝트들
        (의도, 사람 세션만 가능 — S8)                                        (물성, 파라미터만 — S6)     (실행, osiris-stacks — S7)
```

**왜 그래프를 한 번 경유하는가 — 콘솔이 CR을 직접 만들면 안 되는 이유**:

1. **감사 귀속.** 그래프 쓰기는 `:OrgRevision`과 `byPartyId`를 남긴다(`60` §6.3). CR 직접 생성은 k8s audit log에만 남고 조직 감사와 이어지지 않는다.
2. **인가 재사용.** graph-write API는 이미 `authz.CheckDelegation`(DG1~DG5)을 지난다. CR 경로를 새로 만들면 인가 판정이 두 벌이 된다.
3. **`osiris-core`의 권한을 넓히지 않는다.** `70` §7.1이 애써 세운 구분("TokenReview 권한은 워크로드 생성 권한이 아니다")은 core가 어떤 형태로도 워크로드를 소환하지 못한다는 사실 위에 서 있다. core가 CR을 만들면 그 문장이 약해진다 — **CR을 만드는 것은 워크로드를 만드는 것과 실질적으로 같다.**
4. **재해 복구.** 그래프가 진실이면 클러스터를 통째로 재생성해도 선언에서 다시 수렴한다. CR이 진실이면 etcd 백업이 별도의 복구 축이 된다.

### 3.3 그럼에도 남는 비대칭 — 정직하게

에이전트와 스택은 한 가지가 다르다. **에이전트는 전부 같은 모양(Pod 1개)** 이지만 **스택은 종류마다 오브젝트 구성이 다르다**(메일 자가호스팅 = StatefulSet+PVC+Service+Secret, 메일 릴레이 = 작은 Deployment 하나, SCM = 워크로드 0개). 이 차이가 S6(닫힌 카탈로그)의 필요를 만든다 — "모양이 다양하다"를 "모양을 CR이 지정한다"로 풀면 그 순간 CR이 PodSpec을 나르게 되고, 오퍼레이터는 임의 워크로드 생성기가 된다.

**따라서 다양성은 CR이 아니라 카탈로그가 흡수한다.** CR은 "어떤 카탈로그 항목을, 어떤 파라미터로"만 말한다.

### 3.4 커밋은 인프라를 기다리지 않는다

`30` §5.2의 커밋 트랜잭션은 15단계 단일 Neo4j 트랜잭션이다. **스택 프로비저닝은 그 안에 들어가지 않는다.**

- 커밋은 `:CapabilityStackDecl` 노드를 **쓰기**만 한다. MTA가 뜨는 것을 기다리지 않는다.
- 근거: `30` O10이 이미 "정의 완료"와 "프로비저닝 완료"를 두 신호로 분리했다. 스택은 후자에 속한다.
- 결과: DNS 레코드가 아직 전파되지 않아 메일 스택이 `blocked`여도 **조직 커밋은 성공한다.** 능력 키만 `unavailable`일 뿐이다(S2).
- 반대로 했다면: 커밋이 외부 DNS 전파(수 분~수 시간)에 묶이고, 그 대기 중 트랜잭션이 열려 있게 된다 — 온보딩이 사실상 불가능해진다.

### 3.5 신뢰 경계가 넓어지는 지점과 그 봉쇄

**정직한 서술이 먼저다.** 이 설계 이전 오퍼레이터의 권한은 `[실측]` 다음과 같다(`deploy/osiris/templates/rbac-operator.yaml` 전문 확인):

- `osiris-agents` 네임스페이스 **Role**(ClusterRole 아님): `pods` / `persistentvolumeclaims` / `serviceaccounts` / `secrets` / `networkpolicies` / `osiris.dev/agents` + `agents/status`.
- `osiris-system` 네임스페이스 Role: **`coordination.k8s.io/leases`와 `events`뿐.** 파일 주석이 그 의도를 명시한다 — *"osiris-system에는 이 Role이 워크로드 생성 권한을 전혀 주지 않는다"*, *"Team/PermissionProfile CRD에 대한 권한은 아예 없다 — 짓지 않은 권한을 미리 주지 않는다"*.
- 크로스-네임스페이스 RoleBinding으로 `osiris-system`의 SA가 `osiris-agents`의 Role을 쓴다.

즉 **현재 경계는 "에이전트 네임스페이스 안에서만 워크로드를 만든다"이다.** 스택을 도입하면 "임의 인프라 스택을 만든다"로 넓어질 수 있다. 네 겹으로 봉쇄한다.

#### 봉쇄 ① — 카탈로그가 닫혀 있다 (S6)

CRD 스키마 수준의 강제:

```yaml
# crds/capabilitystack.yaml (제안)
spec:
  type: object
  additionalProperties: false          # ★ 알 수 없는 필드는 API 서버가 거부
  required: [stackType, parameters]
  properties:
    stackType:
      type: string
      enum: [mail, scm, ingress]       # ★ 닫힌 열거. 새 종류 = 차트 갱신
    parameters:
      type: object
      additionalProperties: false
      properties: { … 종류별 스칼라·enum·참조만 … }
```

**`podSpec` / `image` / `command` / `args` / `env` / `hostPath` / `nodeName` / `securityContext` 필드가 스키마에 존재하지 않는다.** 존재하지 않는 필드는 `additionalProperties: false` 때문에 표현 자체가 불가능하다. 이것이 "규약"이 아니라 "API 서버의 거부"인 것이 요점이다 — `30` §3.4.2가 F14/O15에 대해 쓴 문장과 같다: *"지켜야 하는 규칙은 그것을 표현 불가능하게 만들어야 지켜진다."*

**검사 가능한 형태**: CRD YAML에 위 6개 필드명이 등장하지 않는지 grep하는 린트 하나면 된다(CS11). 기존 `bin/lint-driver-boundary.sh`류와 같은 성격.

#### 봉쇄 ② — 네임스페이스와 ServiceAccount가 분리된다 (S7)

| 주체 | 네임스페이스 권한 | 못 하는 것 |
|---|---|---|
| `osiris-orchestrator` (기존, 무변경) | `osiris-agents`: 5종+Agent CR / `osiris-system`: leases·events | 스택을 만들 수 없다. `CapabilityStack` CRD에 대한 권한 **0** |
| `osiris-stack-operator` (신규) | `osiris-stacks`: Deployment·StatefulSet·Service·PVC·Secret·ConfigMap·NetworkPolicy·SA + `CapabilityStack` CR / `osiris-system`: **`ingresses` 중 `resourceNames: [osiris-console]` 만** + 그 TLS Secret 1개 | 에이전트를 만들 수 없다. `osiris-agents`에 대한 권한 **0**. `osiris-system`의 파드·Deployment·StatefulSet에 대한 권한 **0** |

**`osiris-orchestrator`의 기존 매니페스트는 한 줄도 바뀌지 않는다.** 이것이 이 배치의 핵심 성질이다 — 실측으로 확인한 그 좁은 경계가 그대로 보존된다.

**두 오퍼레이터가 같은 이미지·다른 Deployment·다른 SA인 이유**: 같은 파드에 두 개의 수렴 루프를 넣으면 투영된 SA 토큰이 하나이므로 **권한이 합쳐진다.** 분리는 프로세스가 분리될 때만 실재한다. 대가(파드 +1, 수렴 루프 +1)를 치르고 얻는 것은 "메일 스택 코드의 버그가 에이전트 Pod를 건드릴 수 없다"는 구조적 보증이다.

**`osiris-system`의 Ingress 권한이 예외가 아닌 이유**(S13의 대가): `70` §7.1이 세운 구분을 그대로 적용한다 — TokenReview가 워크로드 생성이 아니듯, **Ingress는 실행 가능한 워크로드가 아니다.** Ingress는 이미 존재하는 Service로 트래픽을 라우팅하는 규칙일 뿐 새 프로세스를 만들지 못한다. 게다가 `resourceNames`로 **이름 하나**에 고정하므로 다른 Ingress를 만들거나 지울 수 없다. `rbac-operator.yaml`이 leases/events에 대해 쓴 논거(*"여기 나열된 두 리소스 중 어느 것도 실행 가능한 워크로드를 만들지 못한다"*)와 정확히 같은 형태다.

#### 봉쇄 ③ — 선언을 쓸 수 있는 주체가 좁다 (S8)

| 주체 | 스택 선언 쓰기 | 근거 |
|---|---|---|
| `org.admin`/`org.manage.stacks` 보유 `:Person` 세션 | **가능** | 유일한 정상 경로 |
| master-key 세션(1회차) | **가능** — 단 `currentOrgRevision == 0`일 때만 | `60` §4.1의 유일한 `:Party` 없는 세션. §7.6의 조건과 동일하게 좁힌다 |
| genesis 주체(온보딩 컨설턴트) | **불가** | `[실측]` `core/internal/api/server.go`의 genesis 라우트는 `draft`/`status`/`catalog` 3개뿐이고 `genesis.Allows`가 기본 거부다. 새 라우트는 허용목록에 넣지 않으면 자동으로 403 |
| `:AIAgent` 세션 | **불가** | 실행 평면의 주체는 정의 평면에 쓰지 못한다(D1의 `80-action-layer.md` 분리). 추가로 CS12: 스택 선언 쓰기의 `actorPartyId`는 `:Person`이어야 한다 — `20` I15(`IN_ORG`는 `:Person`만)와 **같은 모양의 불변식** |
| 오퍼레이터 자신 | **불가** | 오퍼레이터는 그래프를 **읽기만** 한다. 자기 입력을 스스로 쓸 수 있으면 수렴이 자기참조가 된다 |

**왜 에이전트를 특별히 못박는가**: 에이전트는 외부에서 온 텍스트(메일 본문, 이슈 코멘트, 웹 페이지)를 읽는다. 인젝션 한 줄이 "메일 스택을 선언해라"가 되면, 인젝션의 폭발 반경이 대화에서 **클러스터 인프라**로 넓어진다. 이 문서는 그 경로를 **인가로** 닫는다(프롬프트 지시로 닫지 않는다 — D14가 이미 "프롬프트 인젝션으로 깨지는 규약은 거버넌스가 아님"이라고 못박았다).

#### 봉쇄 ④ — 스택 워크로드도 에이전트와 같은 격리를 받는다

`osiris-stacks` 네임스페이스는 기본 정책이 **egress default-deny**이며, 스택별로 카탈로그가 정한 예외만 열린다(메일 릴레이 = 릴레이 호스트 587/465, 메일 자가호스팅 = 25 아웃바운드 + DNS). 그리고:

- **스택 워크로드는 `osiris-agents`에 도달할 수 없고, 에이전트도 `osiris-stacks`에 도달할 수 없다**(CS14). 에이전트는 메일을 **액션 API를 통해서만** 보낸다 — SMTP 소켓을 직접 열지 않는다. 이것이 D10("에이전트가 아는 호스트명은 3개뿐")의 정신을 스택에 확장한 것이다.
- 스택 워크로드에 `readOnlyRootFilesystem`/`cap_drop: ALL`/`no-new-privileges`/`seccompProfile: RuntimeDefault`를 K6과 동일하게 적용한다. **단 `[미검증]`**: 일부 MTA 이미지가 25번 포트 바인딩을 위해 `NET_BIND_SERVICE`를 요구할 수 있다 — 그 경우 카탈로그가 그 하나만 명시적으로 되돌린다(`cap_add`가 CR 파라미터가 되면 안 된다, 카탈로그에 굳는다).

## 4. 메일 스택 (실사례 ①)

### 4.1 이 스택이 공급하는 키

| 키 | 의미 | 자가호스팅 | 릴레이 |
|---|---|---|---|
| `stk.mail.send` | 조직 명의로 메일을 보낼 수 있다 | ✔ | ✔ |
| `stk.mail.receive` | 외부에서 온 메일이 시스템에 도착한다 | ✔ | **조건부** — §4.2 |
| `stk.mail.address.per-party` | `:Party`마다 고유 주소를 발급할 수 있다 | ✔ | **도메인 소유 여부에 종속** — §6 |

### 4.2 ★ 경계 뒤의 두 모드, 그리고 정직한 비대칭

사용자의 요구는 "자가호스팅이든 외부 SMTP든 스택 내부 사정"이다. 이 요구는 **발신에 대해서는 완전히 성립하고, 수신에 대해서는 그대로 성립하지 않는다.** 숨기지 않고 적는다.

| | 자가호스팅 모드 | 릴레이 모드 |
|---|---|---|
| 발신 | 스택의 MTA가 직접 SMTP 전송 | 프로바이더 submission(587/465)으로 위임 |
| 수신 | MX가 스택을 가리키고 사서함에 저장 | **SMTP 릴레이 자체로는 불가능하다** — SMTP submission은 단방향 프로토콜이다. 수신을 얻으려면 (i) 프로바이더의 inbound 라우팅(웹훅/API)을 함께 쓰거나 (ii) IMAP 사서함을 폴링해야 한다 |
| 필요한 DNS | MX·SPF·DKIM·DMARC (+A/PTR) | SPF(프로바이더 include)·DKIM(프로바이더 셀렉터)·DMARC. **MX는 (i)을 쓸 때만** |
| 필요한 시크릿 | 없음(DKIM 키는 스스로 생성) | 릴레이 자격증명 |

**해법은 모드를 노출하는 것이 아니라 키를 쪼개는 것이다**(S11). 릴레이 모드에서 inbound 경로를 구성하지 않았다면:

```
stk.mail.send    → available
stk.mail.receive → unavailable, reason: "INBOUND_NOT_CONFIGURED"
```

상위 계층은 **여전히 모드를 모른다.** "발신은 되고 수신은 안 되는 설치"라는 사실만 안다 — 그리고 그것이 상위 계층이 실제로 알아야 하는 전부다. S3은 지켜지고, 비대칭은 사라지지 않고 **표현된다.**

> **이것이 사용자가 서술한 대로 되지 않는 유일한 지점이다.** "외부 SMTP면 송수신이 다 되는 것과 등가"는 프로토콜상 참이 아니다. 대신 이 설계는 "그 차이가 상위 계층에 모드로 새지 않는다"는 원래 요구를 온전히 지킨다.

### 4.3 사서함 모델

**온톨로지 델타 제안**(`20-ontology-schema.md` 소유자 확인 필요, §10에 정리):

```
(:Party)-[:HAS_MAILBOX]->(:Mailbox)
```

| `:Mailbox` 속성 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | string | ✔ | `mbx-…` |
| `address` | string | ✔ | 전역 유일(제약 필요) |
| `kind` | enum | ✔ | `hosted`(이 스택이 소유) / `external`(외부 주소를 등록만) |
| `localPart` | string | `hosted`만 | **결정적으로 파생**된다 — CS15 |
| `stackId` | string | `hosted`만 | 어느 스택이 이 사서함을 실체화했는가 |
| `createdAtRevision` / `closedAtRevision` | int | | P4 — 삭제하지 않는다 |

**핵심 결정들**:

1. **`:Person.email`(기존, 필수)은 콘솔 로그인 식별자이고 사서함 주소가 아니다.** 둘은 같을 수도 다를 수도 있다. 섞으면 도메인 변경이 곧 전 직원 로그인 불능이 된다. `20` §3.1의 `email` 필드 의미는 **바뀌지 않는다**.
2. **`:AIAgent`에는 `email` 필드가 없다**(`[실측]` `20` §3.1). 에이전트의 주소는 오직 `:Mailbox`로만 존재한다 — 새 필드를 추가하지 않는다.
3. **`hosted` 사서함의 local part는 LLM이 짓지 않는다**(CS15). `:Party.id`에서 결정적으로 파생하거나 사람이 명시 입력한다. 근거: 컨설턴트가 주소를 창작하면 재실행 때 다른 주소가 나오고(멱등성 붕괴), 인젝션으로 `admin@`·`postmaster@`를 요구할 여지가 생긴다. **예약 local part 목록**(`postmaster`·`abuse`·`admin`·`root`·`noreply`·`mailer-daemon`)은 시스템 소유이며 `:Party`에 배정 불가(CS16).
4. **사람 직원도 주소를 갖는다**(사용자 확정). `hosted` 사서함이 발급되며, 그 사람이 이미 외부 주소를 쓰고 있으면 `external` 사서함으로 등록만 할 수도 있다.
5. **사서함 발급은 커밋의 일부가 아니다.** `:Mailbox` 노드는 커밋에서 만들어지지만, 실제 사서함 실체화는 스택 수렴의 몫이다(§3.4). 스택이 `blocked`면 노드는 있고 사서함은 없다 — 그 상태는 `stk.mail.receive`가 `unavailable`인 것으로 이미 표현된다.

### 4.4 수신 메일이 그래프에서 무엇이 되는가

```
외부 메일  →  [메일 스택]  →  :InboundMessage (불변, 출처 기록)
                                    │
                                    │ 액션 계층의 승격 판정 (D1 소유 — 이 문서는 규정하지 않는다)
                                    ▼
                              :WorkItem (kind: task, executionMode: digital)
                                    │ [:ORIGINATES_FROM]
                                    └──────────▶ :InboundMessage
```

**규칙**:

- `:InboundMessage`는 **append-only**다. 수정·삭제하지 않는다(`:AssignmentDecision`의 C5와 같은 성질).
- **본문은 그래프에 넣지 않는다.** 그래프에는 `rawUri`(오브젝트 저장 위치)와 다이제스트만 둔다. 근거: 그래프는 조직 의도의 저장소이지 메시지 스토어가 아니다(D1). 본문이 그래프에 들어가면 모든 Cypher 조회가 잠재적으로 외부 텍스트를 끌고 들어온다.
- **스택은 본문을 해석하지 않는다**(S12). 파싱·요약·분류는 전부 액션 계층 위쪽의 일이다. 스택이 "이건 업무 요청 같다"고 판단하는 순간 LLM 없는 결정적 계층에 휴리스틱이 들어오고, 그 휴리스틱이 인젝션 대상이 된다.
- **자동 승격은 기본 꺼져 있다.** `:WorkItem` 생성은 (i) 사람이 콘솔에서 승격하거나 (ii) `org.admin`이 명시적으로 켠 정책이 있을 때만 일어난다. 정책의 형태는 D1 소유.

### 4.5 ★ 메일 스택이 반드시 부착하는 출처 메타데이터 (D1의 오염 모델 입력)

**이 절은 필드 목록만 정한다. 이 필드로 무엇을 판정할지는 `80-action-layer.md`가 정한다.** 스택이 이것을 안 채우면 D1의 모델이 근거 없이 돌아가므로, 여기서 **필수**로 못박는다.

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| `origin` | const | ✔ | 항상 `"mail.inbound"` |
| `stackId` | string | ✔ | |
| `receivedAt` | datetime | ✔ | 스택이 수신한 시각(발신자 주장 시각이 아님) |
| `recipientMailboxId` | string | ✔ | 어느 사서함으로 왔는가 |
| `envelopeFrom` | string | ✔ | SMTP MAIL FROM. **`headerFrom`과 별개 필드다** |
| `headerFrom` | string | ✔ | `From:` 헤더. 둘의 불일치 자체가 신호다 |
| `replyTo` | string | | |
| `messageId`, `inReplyTo`, `references` | string / string[] | ✔ / | 스레드 재구성 |
| `authResults.spf` | enum | ✔ | `pass`/`fail`/`softfail`/`neutral`/`none`/`temperror`/`permerror` |
| `authResults.dkim` | enum | ✔ | 위와 동일 척도 + 서명 도메인 `dkimDomain` |
| `authResults.dmarc` | enum | ✔ | `pass`/`fail`/`none` + 정렬(alignment) 결과 |
| `tlsOnDelivery` | bool | ✔ | 마지막 홉이 STARTTLS였는가 |
| `senderKnownPartyId` | string\|null | ✔ | 그래프에 그 주소의 `:Mailbox`가 있으면 그 소유 `:Party`. **없으면 반드시 null** — 추측하지 않는다 |
| `externalTrust` | enum | ✔ | `unauthenticated` / `domain-authenticated`(DMARC pass) / `known-party`(위 + `senderKnownPartyId` 존재) |
| `attachmentCount`, `attachments[].{filename, mediaType, sizeBytes, sha256}` | | ✔ | **첨부는 절대 자동 열람·실행되지 않는다.** 스택은 다이제스트만 남긴다 |
| `rawUri`, `rawSha256`, `sizeBytes` | string/string/int | ✔ | 원문 위치와 무결성 |
| `listUnsubscribe`, `autoSubmitted`, `precedence` | string | | 자동 발송 메일 식별용(루프 방지) |

**스택이 지켜야 할 세 가지 규율**:

1. **`Authentication-Results` 헤더는 신뢰 경계 안에서 스택이 직접 계산한 값만 기록한다.** 외부에서 도착한 동명 헤더는 **제거(strip)** 한 뒤 자신의 것을 삽입한다. 이것을 안 하면 발신자가 `dmarc=pass`를 스스로 써서 보낼 수 있다 — 오염 모델 전체가 무의미해진다.
2. **`externalTrust`는 파생값이며 스택이 계산한다.** 소비 측이 spf/dkim/dmarc 세 값을 각자 조합하면 조합 규칙이 여러 벌 생긴다(C-3의 단일 해석기 원칙과 같은 이유).
3. **어떤 필드도 "모르면 낙관적으로" 채우지 않는다.** 판정 불가는 `none`/`temperror`/`null`이지 `pass`가 아니다.

### 4.6 발신 측 출처 규율

- 에이전트는 SMTP를 직접 열지 않는다(§3.5 봉쇄 ④). 발신은 액션 API 경유이며, 액션 계층이 `stk.mail.send`를 요구한다.
- 스택은 발신 메일에 **조직 귀속 헤더**를 삽입한다(`X-OSiris-Party-Id`, `X-OSiris-WorkItem-Id`, `X-OSiris-Revision`). 목적은 답장이 돌아왔을 때 스레드를 그래프에 다시 붙이는 것이다.
- **자동 응답 루프 방지**: 스택은 `Auto-Submitted: auto-generated`를 삽입하고, 그 헤더가 있는 수신 메일은 `:WorkItem` 승격 후보에서 자동 제외한다(승격 정책은 D1 소유이지만, **루프 차단은 스택의 안전 책임**이다).

### 4.7 DNS 레코드와 그 검증

**필요한 레코드**(자가호스팅 모드 기준):

| 레코드 | 예시 형태 | 누가 값을 정하는가 | 검증 방법 |
|---|---|---|---|
| `MX` | `mail.<domain>. 10` | 스택이 제시 | MX 조회 → 우리 호스트를 가리키는지 |
| `A`/`AAAA` (mail 호스트) | `mail.<domain> → <외부 IP>` | 사람(자기 IP를 안다) | 조회 후 대조 |
| `TXT` SPF | `v=spf1 ip4:<IP> -all` (릴레이면 `include:<provider>`) | 스택이 제시 | TXT 조회 후 문자열 포함 검사 |
| `TXT` DKIM | `<selector>._domainkey → v=DKIM1; k=rsa; p=<공개키>` | **스택이 키쌍을 생성**하고 공개키를 제시 | 조회한 `p=` 값과 보유 공개키의 정확 일치 |
| `TXT` DMARC | `_dmarc → v=DMARC1; p=quarantine; rua=…` | 스택이 제시(정책 강도는 사람이 선택) | 조회 후 파싱 |
| `PTR` (역방향) | `<IP> → mail.<domain>` | **우리가 만들 수 없다** — IP 소유자(호스팅 사업자)의 몫 | 조회만. 불일치는 **경고**이지 오류가 아니다 |

**검증의 성질**:

- OSiris는 **조회하고 대조하고 보여준다**(S10). DNS 프로바이더 API 자격증명을 받지 않는다. 사용자 판단: 도메인 전체를 다시 쓸 수 있는 자격증명을 시스템이 보유하는 것은 스택 하나가 주는 편의보다 비싸다.
- 화면에는 **만들어야 할 레코드의 정확한 문자열**과 **현재 조회 결과**를 나란히 보여준다. "SPF를 설정하세요"가 아니라 "이 줄을 그대로 넣으세요 / 지금 조회되는 값은 이것입니다".
- **검증 상태 4종**: `absent`(레코드 없음) / `mismatch`(있는데 다름) / `match` / `propagating`(TTL 안에 최근 변경 관측). `propagating`은 사람에게 "기다리면 된다"를 말하기 위해 필요하다.
- 검증은 **주기적**(기본 5분, 스택이 `blocked`인 동안)이고, 전부 `match`가 되는 순간 자동으로 수렴을 재시도한다 — 사람이 "다시 확인" 버튼을 누를 필요가 없다.
- **`[미검증]`**: 클러스터 안에서의 DNS 조회는 `kube-dns`를 거치며, 캐시된 부정 응답(NXDOMAIN 캐시)이 `propagating` 판정을 흐릴 수 있다. 외부 리졸버(8.8.8.8 등)를 직접 쓸지 여부는 egress 정책과 얽히므로 실측이 필요하다.
- **PTR은 성공 조건에 넣지 않는다.** 우리가 통제할 수 없는 것을 성공 조건에 넣으면 스택이 영원히 `blocked`가 된다. 대신 배달률 경고로만 표시한다.

### 4.8 프롬프트 인젝션에 대해 이 문서가 **하지 않는** 말

수신 메일 본문은 신뢰할 수 없는 외부 텍스트다. **그 텍스트를 에이전트가 어떻게 다루는지, 어떤 오염 라벨이 붙는지, 어떤 액션이 차단되는지는 전부 `80-action-layer.md`(D1)가 소유한다.** 이 문서는 §4.5의 필드를 채워 넣을 뿐이다. 두 문서가 같은 규칙을 각자 적으면 반드시 어긋나므로, 여기서는 **의도적으로 침묵**한다.

## 5. SCM/CI 스택 (실사례 ②) — 일반화의 증명

### 5.1 무엇이 같고 무엇이 다른가

| 축 | 메일 | SCM/CI |
|---|---|---|
| 공급 키 | `stk.mail.{send,receive,address.per-party}` | `stk.scm.repo.{read,write}` · `stk.scm.webhook` · `stk.ci.run` · `stk.scm.credential.rotate` |
| 워크로드 | 자가호스팅 = 여러 개 / 릴레이 = 1개 | **0개 또는 1개(웹훅 수신 어댑터)** |
| 모드 | selfhosted / relay | **외부(GitHub 등)만.** 자가호스팅 변형이 현재 없다 |
| DNS 의존 | 강함 | 웹훅에만(=`stk.ingress.public` 의존) |
| 자격증명 | 릴레이 자격증명(선택) | PAT/앱 설치 토큰(필수) |

**이 표가 모델의 일반성을 증명하는 지점 두 개**:

1. **워크로드를 하나도 만들지 않는 스택이 존재한다.** SCM 스택의 프로비저닝은 "자격증명을 저장하고, 조직/레포 접근을 확인하고, 웹훅을 등록한다"이다. 즉 **능력 스택은 "파드 묶음"의 동의어가 아니라 "선택적으로 존재하는 능력의 단위"** 다. 정의(§2.1)가 워크로드를 언급하지 않은 것은 우연이 아니다.
2. **모드가 하나뿐인 스택도 같은 모델을 쓴다.** 모드가 하나라고 경계를 없애면, 나중에 자가호스팅 Forgejo/GitLab 변형이 생길 때 전면 재작업이 된다. 경계는 선택지가 둘일 때 만드는 것이 아니라 **선택지가 하나일 때 미리 두는 것**이다(`10` §2.3의 이음새 논리와 동형).

### 5.2 부분 공급 — 웹훅만 못 쓰는 경우

`stk.scm.webhook`은 `stk.ingress.public`에 의존한다(외부에서 우리에게 HTTP가 들어와야 한다). 도메인 없는 설치에서:

```
stk.scm.repo.read   → available
stk.scm.repo.write  → available
stk.ci.run          → available          (우리가 나가서 트리거하므로)
stk.scm.webhook     → unavailable, reason: "DEPENDS_ON_stk.ingress.public"
```

그리고 **폴링 폴백**: 웹훅이 없으면 어댑터가 주기 폴링으로 같은 사실을 늦게 관측한다. 이때 `stk.scm.webhook`은 여전히 `unavailable`이고(웹훅은 정말 없다), 이벤트 신선도가 떨어지는 것은 **소비 측이 아는 사실**이 된다. "폴링으로 대체했으니 available로 치자"는 **금지**한다 — 키가 거짓말을 하기 시작하면 계약 전체가 무너진다(CS3).

### 5.3 이 스택이 닫는 기존 갭

`31-onboarding-boundary.md` §2.2가 **[갭] 신규 발견**으로 기록한 항목:

> *"에이전트별 git PAT(읽기 전용 스코프, §8.4) … 최초 값을 누가 어디서 입력하는지 미정 … 대표가 GitHub PAT를 어디서 입력하는가가 없다"*(`31` §2.2)

**SCM 스택이 그 입력 경로다.** 스택 선언 화면이 조직 수준 자격증명을 받고, 에이전트별 토큰은 그로부터 파생·발급된다(`10` §8.4가 요구한 "드라이버가 발급/주입"의 상류가 이제 존재한다). 자격증명은 `osiris-stacks`의 Secret에만 살고, 에이전트에는 **파생된 좁은 토큰만** 파일 주입된다(G5 준수).

**`[미검증]`**: GitHub의 어떤 자격증명 종류(fine-grained PAT / GitHub App installation token)가 "조직 수준 원본 → 에이전트별 좁은 파생"을 실제로 지원하는지 확인하지 않았다. `31` §1.3 Q2b가 요구하는 **교환 경로 확인**이 여기서 반드시 수행되어야 한다 — 확인 없이 원본 PAT를 저장하면 사건 4의 재발이다.

## 6. 도메인 없는 설치

### 6.1 무엇이 꺼지고 무엇이 살아남는가

| | 도메인 없음(루프백) | 도메인 있음 |
|---|---|---|
| 클러스터 기동·전 서비스 healthy | ✔ | ✔ |
| 콘솔 접근 | `kubectl port-forward` / NodePort / 로컬호스트 | 공개 호스트명 + TLS |
| `stk.ingress.public` / `stk.ingress.tls` | `unavailable` | `available` |
| OmniRoute 경유 LLM 호출 | ✔ (아웃바운드만 필요) | ✔ |
| 에이전트 생성·배정·업무 | ✔ | ✔ |
| 직원 등록 티켓 | ✔ — 대역외 전달(H12 기본) | ✔ |
| `stk.mail.send` | **조건부** — §6.2 | ✔ |
| `stk.mail.receive` | **불가** (MX를 걸 도메인이 없다) | ✔ |
| `stk.mail.address.per-party` | **불가** (local part를 붙일 도메인이 없다) | ✔ |
| `stk.scm.repo.*` / `stk.ci.run` | ✔ | ✔ |
| `stk.scm.webhook` | `unavailable` | ✔ |

**요점**: 도메인 부재가 끄는 것은 **주소를 갖는 것**과 **외부에서 들어오는 것** 둘뿐이다. 조직을 정의하고 에이전트를 돌리고 업무를 배정하는 **제품의 본체는 전부 살아 있다.**

### 6.2 도메인 없이 발신이 가능한 좁은 경우

릴레이 모드에서 발신 주소가 **릴레이 프로바이더가 소유한 도메인**일 때(예: 운영자의 기존 메일 계정) 발신 자체는 성립한다. 이때:

- `stk.mail.send` → `available`
- `stk.mail.address.per-party` → `unavailable` — 모든 발신이 **하나의 주소**에서 나가고, 개별 귀속은 §4.6의 `X-OSiris-*` 헤더와 `Reply-To`로만 표현된다.
- `stk.mail.receive` → 프로바이더 inbound 웹훅을 쓰면 가능하지만 그 웹훅이 `stk.ingress.public`을 요구한다 → 루프백에서는 `unavailable`.

**이것이 키를 셋으로 쪼갠 이유의 실증이다.** "메일 스택 있음/없음"으로는 이 상태를 표현할 수 없다.

### 6.3 H12는 뒤집히지 않는다 — 명확화될 뿐

`60-identity-authn.md` H12 원문:

> *"직원의 최초 자격증명은 **1회용 등록 티켓**으로 시작하고, 전달은 **기본적으로 대역외**(대표가 콘솔에서 1회 열람 → 사람에게 직접)다. 이메일/SMTP 의존을 만들지 않는다"*(`60` §0 H12)

그리고 §5.2가 그 근거를 밝힌다:

> *"등록 경로가 메일 서버를 요구하는 순간 '어디서든 `install osiris` → 루프백 UI'가 거짓이 된다."*(`60` §5.2)

**정합 논증 (세 단계)**:

1. **H12가 금지하는 것은 "의존"이지 "메일"이 아니다.** §5.2의 표는 이미 SMTP를 *"기본값에서 기각"* 이라고 적었지 *"영구 금지"* 라고 적지 않았고, 세 번째 행에서 알림 어댑터 경유를 *"선택 기능으로 열어둠 — 없어도 정상 동작"* 으로 명시했다. 메일 스택은 **그 세 번째 행의 새 인스턴스**다.
2. **능력 스택 모델은 "의존 없음"을 계약으로 강제한다.** C-8(부재는 부재만 일으킨다)과 CS2가 "메일이 없어도 등록 경로가 완전하다"를 **테스트 가능한 성질**로 만든다. H12가 서술로 요구하던 것이 이제 계약이 된다 — **H12는 약해지는 것이 아니라 강해진다.**
3. **재검토 트리거가 발화하지 않는다.** `60` §12 결정표는 H12의 재검토 조건을 *"SMTP 또는 알림 어댑터가 **기본 구성**이 되면(현재는 선택)"*(`60` §12)으로 적어 두었다. 메일 스택은 **기본 미선언**이다 — `helm install` 직후 메일 스택은 존재하지 않고, 선언은 사람이 온보딩 3단계에서 명시적으로 해야 한다. 따라서 트리거 조건이 성립하지 않는다.

**한 가지 격상은 허용한다**: 메일 스택이 `healthy`이고 그 `:Person`에게 사서함이 있으면, 관리자가 등록 티켓을 **"메일로 보내기"로 선택**할 수 있다. `60` §5.2가 알림 어댑터에 대해 이미 허용한 것과 **동일한 격상**이며, 기본값은 여전히 대역외다(CS17).

### 7.1 단계 0 — LLM 게이트웨이

| | |
|---|---|
| **입력** | OmniRoute 관리자 비밀번호(1회, 메모리만) → 매니지 키 교환 / 프로바이더 API 키 / 별칭 매핑 확인 |
| **산출** | `.env` 또는 Secret의 `OSIRIS_OMNIROUTE_MANAGE_KEY`·`OSIRIS_GATEWAY_TOKEN` / OmniRoute DB의 프로바이더·별칭 / **egress 허용목록 ConfigMap 갱신(신규, S15)** / 그래프 쓰기 **0건**(O14) |
| **현 구현** | **대부분 구현됨.** `[실측]` `api/internal/onboarding/handlers.go`에 `step0Status`·`verifyGateway`·매니지 키 교환·`PropagatedToOrchestrator` 확인이 존재하고 `Ready` 술어가 계산된다. **egress 허용목록 동기화는 미구현** |

#### 7.1.1 egress 허용목록 갭의 폐쇄 (S15)

`31-onboarding-boundary.md` §2.3(사용자 지시의 `31 §202`)이 기록한 갭:

> *"온보딩이 프로바이더를 등록해도, 그 프로바이더의 실제 도메인이 egress 허용목록에 없으면 추론 호출이 강제 계층(egress 프록시)에서 거부된다. 온보딩 0단계의 성공 판정이 '게이트웨이 헬스'만 본다면 이 실패를 못 잡는다"*(`31` §2.3)

**현 상태의 정확한 진단** `[실측]`:

- `egress/squid.conf`에 `acl llm_provider_domains dstdomain api.anthropic.com` / `api.openai.com` 등이 **정적으로** 박혀 있다.
- k8s에서는 그 파일이 `deploy/osiris/templates/egress-deployment.yaml` 안의 **ConfigMap `egress-squid-conf`에 인라인**으로 들어간다. 즉 허용목록 갱신 = ConfigMap patch.
- **부분적으로는 이미 닫혀 있다**: `30` O16이 추가한 0-6(실제 추론 1회, `stream:true`)은 egress를 실제로 통과하므로 차단 시 여기서 **드러난다**. 갭은 "전혀 못 잡는다"가 아니라 **"잡히긴 하는데 원인을 구별할 수 없고 자동 수정 경로가 없다"** 로 좁혀져 있다 — 프록시 거부(403 from proxy)와 키 무효(401 from provider)를 관리자가 구분할 수 없다.

**폐쇄 설계**:

| # | 내용 |
|---|---|
| **0-2b (신규 단계)** | 프로바이더 등록 직후, **프로바이더→도메인 고정표**(차트/이미지의 정적 자산)에서 필요한 도메인 집합을 구하고 `egress-squid-conf` ConfigMap을 patch한다. **자유 입력 금지** — 표에 없는 프로바이더는 등록 자체를 거부한다(온보딩 폼이 방화벽 우회 수단이 되는 것을 막는다) |
| **반영 강제** | `70` §10.5가 실측으로 기록한 함정 — *"ConfigMap/Secret 값 변경은 파드를 롤아웃시키지 않는다 … 세 번 반복됐다"*. 따라서 patch 후 **checksum 애노테이션 갱신에 의한 롤아웃** 또는 `squid -k reconfigure` 중 하나를 반드시 수행하고, **수행했다는 사실을 확인**한다(설정 파일이 바뀐 것과 프로세스가 그것을 읽은 것은 다른 사실이다) |
| **0-5 성공 판정에 술어 추가** | (d) **등록된 모든 프로바이더의 도메인이 실행 중인 squid 설정에 존재한다** — 파일이 아니라 실행 중 설정을 본다 |
| **0-6 실패의 원인 분해** | 0-6이 실패했을 때 응답 코드/프록시 로그로 `EGRESS_BLOCKED` / `PROVIDER_AUTH_FAILED` / `GATEWAY_DOWN`을 구분해 보고한다. 이것이 "잡히긴 하는데 원인을 모른다"를 닫는 부분 |
| **누가 patch하는가** | `osiris-stack-operator`가 아니라 **`osiris-orchestrator`** — `70` §10.5가 NATS ConfigMap에 대해 이미 같은 권고를 했다(*"권고: operator가 ConfigMap을 patch하고 reload는 파일 변경 감지에 맡긴다"*). 같은 성격의 권한을 한 주체에 모은다. `rbac-operator.yaml`에 `osiris-system`의 `configmaps` patch 권한(`resourceNames`로 2개 고정)이 필요하다 — **[이 문서가 요구하는 매니페스트 변경]** |

### 7.2 단계 1 — 조직 정체성

| | |
|---|---|
| **입력** | 조직명 / 법인명 / 타임존 / **DNS 도메인(선택, S9)** |
| **산출** | `:Organization:Party` 갱신, `:OrgRevision{n:0}` 존재 확인. 도메인이 있으면 `dnsDomain`·`mailDomain` 기록 |
| **현 구현** | **부분.** `[실측]` `core/internal/graphdb/seed.go:seedOrganization`이 `name`/`legalName`/`timezone`을 MERGE한다. **도메인 필드는 스키마에도 코드에도 없다.** 또한 현재는 부트스트랩 시드 경로로 호출되며 온보딩 대화가 값을 넣는 경로가 아니다 |
| **건너뛰면** | 도메인 관련 스택(2·3·7의 웹훅)이 전부 `blocked`. 조직 자체는 성립하므로 나머지는 정상 |

**도메인이 하나의 값에서 부챗살처럼 퍼지는 지점**(이것이 도메인을 1단계에 두는 이유):

```
:Organization.dnsDomain
      ├─▶ 콘솔 호스트명            → 2단계 (stk.ingress.public)
      ├─▶ Ingress TLS(ACME) 대상   → 2단계 (stk.ingress.tls)
      ├─▶ :Mailbox.address의 도메인 → 3단계 (stk.mail.address.per-party)
      ├─▶ SPF/DKIM/DMARC 레코드     → 3단계 (§4.7)
      └─▶ SCM 웹훅 수신 URL        → 7단계 (stk.scm.webhook)
```

**한 값이 다섯 곳에 퍼지므로 그 값은 단 한 곳에 있어야 한다** — `:Organization`이다. 각 스택이 자기 도메인 파라미터를 따로 갖는 설계는 명시적으로 기각한다(D1의 "같은 사실을 두 곳에 두지 않는다").

### 7.3 단계 2 — 진입 경로 (선택)

| | |
|---|---|
| **입력** | 콘솔 호스트명(기본 `<dnsDomain>` 또는 `osiris.<dnsDomain>`) / TLS 모드(`provided`: 사람이 인증서 제공 / `acme`: cert-manager 위임) |
| **산출** | `:CapabilityStackDecl{type:'ingress'}` → CR → `osiris-system`의 Ingress 1개(이름 고정) + TLS Secret 참조 |
| **현 구현** | **미구현(스택으로서).** `[실측]` 차트에 `templates/ingress.yaml`이 있고 `values.yaml`의 `ingress.host`/`tlsSecretName`이 **기본 빈 문자열**이라 도메인 없는 설치는 이미 지원된다. 온보딩이 이 값을 바꾸는 경로는 없다 |
| **건너뛰면** | 콘솔은 port-forward/NodePort로만 접근. `stk.ingress.public`·`stk.ingress.tls` 부재 → `stk.scm.webhook`도 부재(§5.2). 그 외 전부 정상 |

**ACME의 정직한 한계**: 이 차트는 cert-manager를 번들하지 않는다. `acme` 모드는 클러스터에 cert-manager CRD가 이미 있을 때만 성립하며, 없으면 스택은 `blocked{reason:"CERT_MANAGER_ABSENT"}`가 된다. **차트가 cert-manager를 자동 설치하지 않는 이유**: 그것은 클러스터 전역 컴포넌트이고, `helm install osiris` 하나가 클러스터 전역 상태를 바꾸는 것은 K1("설치 패키지 하나")의 의미를 넘어선다.

#### 7.6.1 누가 커밋을 부르는가 — F14 이후의 공백을 메운다

**현재 상태의 정확한 서술**:

- `[실측]` `core/internal/genesis/genesis_test.go`에 `{http.MethodPost, "/v1/onboarding/commit"}`가 **거부되어야 할 경로**로 잠겨 있다(주석: *"★ F14 — the whole point"*). `genesis.Allows`는 기본 거부 허용목록이다.
- `30` §3.4.3은 커밋 주체를 *"승인한 사람의 세션"* 으로 규정했다.
- **그런데 그 사람 세션용 커밋 엔드포인트는 어디에도 만들어지지 않았다.** F14는 문 하나를 닫았고, 반대편 문은 설계 문장으로만 존재한다.

**결정 (S14)**:

```
콘솔  ──POST /api/onboarding/commit──▶  osiris-api
                                          │ ① 세션 인증(사람 세션만)
                                          │ ② 인가: 1회차 = kind:"master-key" 세션,
                                          │        2회차+ = org.admin 보유 :Person (DG1~DG5)
                                          ▼
                        osiris-core  POST /v1/onboarding/commit
                                          (core API 토큰 + actor 헤더 — genesis 토큰 아님)
                                          │ ③ genesisAuth 미들웨어를 타지 않는다
                                          │    → F14의 잠금은 그대로 유효
                                          ▼
                                    §9.2 15단계 단일 트랜잭션
```

- **F14는 뒤집히지 않는다.** genesis 주체는 여전히 이 경로를 부를 수 없고, `genesis_test.go`의 잠금은 계속 통과한다. 이 문서가 하는 일은 **다른 인증 방식의 문을 명세**하는 것이다. `core/internal/api/server.go`의 주석(*"★ THERE IS ALSO NO POST /v1/onboarding/commit"*)은 "만들면 안 된다"가 아니라 "genesis 경로에는 없다"의 기록으로 읽어야 하며, 새 라우트는 `s.auth`(core API 토큰) 아래 달린다 — 기존 writeop들과 **동일한 배선**이다.
- **`60` §6.5와의 긴장, 그리고 좁은 명확화**: §6.5는 *"actorPartyId가 유효한 `:Party`가 아니면 core는 mutating 요청을 거부"* 한다. 그런데 1회차 커밋의 호출자(master-key 세션)에는 `:Party`가 없다. **뒤집지 않고 좁게 명확화한다**:

  > **`60` §6.5 명확화(이 문서가 제안)**: 최초 온보딩 커밋에 한해, `actorPartyId`는 **그 트랜잭션이 만드는** `:Person`을 가리킬 수 있다. core는 §9.2 단계 11(멤버십) 이후·커밋 이전에 그 `:Party`의 존재를 검증한다. 이 면제는 **`currentOrgRevision == 0` ∧ 세션 `kind == "master-key"` ∧ 그 사람이 `org.admin` 멤버십을 갖는 대상일 때**만 성립한다(CS18).

  이는 `30` §3.4.3이 이미 서술한 자기귀속(*"byPartyId = 그 커밋이 만드는 초기 관리자"*)을 **core의 검사 순서**로 번역한 것이다. 새 예외가 아니라 기존 서술의 집행 형태다.

#### 7.6.2 15단계 트랜잭션의 부분 실패

`30` O9는 "단일 트랜잭션 + 네이티브 ROLLBACK, 사가 불필요"로 결단했다. 그 결단은 유효하지만, **트랜잭션이 감싸지 못하는 것들**이 있고 그것을 여기서 열거한다.

| 실패 지점 | 트랜잭션이 막아주는가 | 처리 |
|---|---|---|
| 검증(I1~I17) 실패 | ✔ ROLLBACK. 그래프에 아무것도 남지 않음 | 오류 목록 반환. `30` §5.2 그대로 |
| 리허설 실패 | ✔ ROLLBACK | 후보별 탈락 사유 반환 |
| Neo4j 연결 끊김 | ✔ 서버측 트랜잭션 자동 abort | 재시도 — 아래 |
| **트랜잭션 타임아웃** | ✔ (전부 롤백) | **명시적 상한을 둔다.** 대규모 조직에서 15단계+리허설이 기본 타임아웃을 넘길 수 있다. 상한 초과는 `COMMIT_TIMEOUT`으로 **전부 실패**이며 부분 성공이 아니다. `[미검증]` — 실제 소요 시간은 조직 규모별 실측이 필요하다 |
| **클라이언트 연결 끊김 (커밋 직전/직후)** | ✖ **호출자가 결과를 모른다** | 아래 `expectedRevision`으로 해소 |
| `org.revision` 이벤트 발행 실패(NATS) | ✖ 커밋은 이미 durable | **치명적이지 않다.** 수렴 루프가 어차피 15초 주기로 돌므로(`10` §1.4) 최대 15초 지연될 뿐이다. 이벤트는 **가속 장치이지 정확성의 근거가 아니다** |
| 스택 프로비저닝 실패 | ✖ 애초에 트랜잭션 밖 | §3.4 — 커밋은 인프라를 기다리지 않는다. 스택은 `blocked`로 남고 키만 `unavailable` |

**`expectedRevision` 선행조건 (S14의 후반부)**:

```jsonc
POST /v1/onboarding/commit
{ "draft": {...}, "expectedRevision": 0, "idempotencyKey": "<draftId>-<sha256(draft)>" }
```

- core는 트랜잭션 안에서 `currentOrgRevision == expectedRevision`을 확인하고, 다르면 **409 `REVISION_CONFLICT`** 로 거부한다.
- 효과 ①: 연결이 끊겨 결과를 모르는 클라이언트가 **그냥 재시도해도 안전**하다. 첫 시도가 성공했다면 두 번째는 409로 거부된다(리비전이 이미 1이므로) — **이중 증가가 구조적으로 불가능**하다.
- 효과 ②: 두 관리자가 동시에 서로 다른 초안을 커밋하는 경쟁에서 나중 것이 조용히 이기는 일이 없다.
- 효과 ③: 모든 쓰기가 MERGE 멱등(`20` §9.1)이라는 기존 성질과 결합해, "재시도 안전"이 **관례가 아니라 술어**가 된다.

## 8. 불변식 (CS1~CS18)

기계 검사 가능성을 마지막 열에 적는다. "린트"는 소스/매니페스트 정적 검사, "런타임"은 core의 판정, "CI"는 테스트를 뜻한다.

| # | 불변식 | 위반 시 | 검사 |
|---|---|---|---|
| **CS1** | 능력 키는 `^stk\.[a-z0-9-]+(\.[a-z0-9-]+){1,2}$`를 만족하고, `cap.`으로 시작하는 문자열은 능력 키가 **아니다**. 두 이름공간은 교집합이 공집합 | 오류 | 린트(정규식) + CI |
| **CS2** | 어떤 키가 `unavailable`이어도, 그 키를 요구하지 않는 액션·경로·판정의 결과는 **바뀌지 않는다** | 오류 | CI(전 키를 unavailable로 고정한 상태에서 기존 테스트 전량 통과) |
| **CS3** | 키의 `state`는 실제 능력과 일치한다 — 폴백·우회로 능력을 흉내 내고 `available`로 보고하지 않는다 | 오류 | 코드 리뷰 + 스택별 헬스 정의 검토(자동 검사 불가, `[갭]`) |
| **CS4** | `:ActionType.requiresCapability`의 모든 원소는 정적 레지스트리에 존재한다 | 정의 시점 오류(생성 거부) | 런타임(writeop 검증) + 린트 |
| **CS5** | 능력 해석 응답에 `mode` 또는 그와 동등한 구현 식별 정보가 **없다** | 오류 | 린트(응답 스키마) |
| **CS6** | 한 액션 판정 안에서 같은 키는 한 스냅샷으로만 평가된다 | 오류 | CI |
| **CS7** | `osiris-core` 외의 어떤 컴포넌트도 능력 상태를 자체 캐시하지 않는다 | 오류 | 린트(`/v1/capabilities` 호출부 검사) |
| **CS8** | 스택 의존은 키 단위로만 선언된다(스택 ID에 대한 의존 금지) | 오류 | 린트(카탈로그 스키마) |
| **CS9** | 한 스택이 공급하는 키들은 **서로 다른 state를 가질 수 있다** — "스택이 healthy면 모든 키가 available"을 가정하는 코드가 없어야 한다 | 오류 | CI |
| **CS10** | 키 의존 그래프에 사이클이 없다 | 빌드 실패 | 린트(정적 레지스트리) |
| **CS11** | `CapabilityStack` CRD 스키마에 `podSpec`·`image`·`command`·`args`·`env`·`hostPath` 필드가 존재하지 않고, 모든 object 노드가 `additionalProperties: false`다 | 빌드 실패 | 린트(CRD YAML grep) |
| **CS12** | 스택 선언(`:CapabilityStackDecl`)의 `actorPartyId`는 `:Person`이거나, `currentOrgRevision == 0`인 master-key 세션이다. `:AIAgent`는 어떤 경우에도 불가 | 오류 | 런타임(core writeop) + CI |
| **CS13** | 릴레이 자격증명으로 **사람의 계정 비밀번호**를 저장하지 않는다 — 앱 전용 비밀번호/API 키만 허용 | 오류 | `31` §5.5 계열 린트(human-facing-secret 영속화 금지) |
| **CS14** | `osiris-agents`와 `osiris-stacks` 사이에 어느 방향으로도 네트워크 도달이 없다 | 오류 | `bin/verify-isolation-k8s.sh` 확장(기존 스크립트의 규율 계승: 실행 불가한 검사는 조용히 통과시키지 않고 SKIP으로 명시) |
| **CS15** | `hosted` 사서함의 local part는 `:Party.id`에서 결정적으로 파생되거나 사람이 명시 입력한 값이다. LLM 출력이 직접 들어가지 않는다 | 오류 | 코드 경로 검사 + CI(같은 입력 → 같은 주소) |
| **CS16** | 예약 local part(`postmaster`·`abuse`·`admin`·`root`·`noreply`·`mailer-daemon`)는 어떤 `:Party`에도 배정되지 않는다 | 오류 | 런타임 + CI |
| **CS17** | 등록 티켓의 **기본** 전달 경로는 대역외다. 메일 전달은 관리자의 명시적 선택으로만 발생한다(H12 보존) | 오류 | CI(메일 스택 healthy인 상태에서도 기본 응답이 대역외인지) |
| **CS18** | `:Party` 없는 mutating 요청은 **최초 온보딩 커밋 하나뿐**이며, `currentOrgRevision == 0` ∧ master-key 세션 ∧ 대상 `:Person`이 그 트랜잭션 안에서 생성됨을 전부 만족할 때만 허용된다 | 오류 | 런타임(core) + CI(음성 케이스 다수) |

## 9. 이 문서가 기존 결정을 수정·명확화한 지점 (전수)

정직하게 전부 나열한다. "조용히 바꾸지 않는다"는 이 저장소의 규율이다.

| 대상 | 성질 | 내용 |
|---|---|---|
| `60` H12 / §5.2 | **명확화(뒤집지 않음)** | 메일은 선택적 능력 스택으로 도입되며 기본 미선언이다. 등록 티켓의 기본 전달은 대역외 그대로(CS17). `60` §12의 H12 재검토 트리거(*"기본 구성이 되면"*)는 발화하지 않는다. §6.3의 3단계 논증 참조 |
| `60` §6.5 | **좁은 명확화** | 최초 온보딩 커밋에 한해 `actorPartyId`가 같은 트랜잭션 내에서 생성되는 `:Person`을 가리킬 수 있다. 세 조건 전부 만족 시에만(CS18). `30` §3.4.3의 자기귀속 서술을 core의 검사 순서로 번역한 것 |
| `30` §3.4.3 / F14 | **공백 보충(뒤집지 않음)** | F14가 닫은 genesis 경로는 그대로 두고, 사람 세션용 `POST /api/onboarding/commit` → `POST /v1/onboarding/commit`(core API 토큰, `s.auth` 배선)을 신설한다. `genesis_test.go`의 잠금은 계속 유효 |
| `30` §5.2 / O9 | **보강** | 단일 트랜잭션 + 네이티브 롤백은 유지. `expectedRevision` 선행조건과 `COMMIT_TIMEOUT`·이벤트 발행 실패의 처리를 추가로 명세(§7.6.2) |
| `31` §2.3 (사용자 지시의 `31 §202`) | **갭 폐쇄 설계** | 0-2b 신설 + 0-5 성공 판정에 술어 (d) 추가 + 0-6 실패 원인 분해. 갭이 O16의 0-6으로 **부분적으로는 이미 닫혀 있었다**는 사실도 함께 기록(§7.1.1) |
| `31` §2.2 B2 (git PAT 입력 경로 부재) | **갭의 지정 해소 지점** | 7단계 SCM 스택이 그 경로다. 단 교환 경로 확인은 `[미검증]`으로 남는다(§5.3) |
| `70` K5 / `rbac-operator.yaml` | **비수정 확인 + 인접 추가** | 기존 orchestrator RBAC은 **한 줄도 바꾸지 않는다**. 새 권한은 별도 SA(`osiris-stack-operator`)에 붙는다. 예외로 `osiris-orchestrator`에 `osiris-system`의 configmaps patch(`resourceNames` 2개 고정)가 필요하다 — `70` §10.5의 NATS ConfigMap 권고와 같은 항목이므로 새 요구가 아니라 **이미 예고된 요구의 병합** |
| `70` §2 (네임스페이스 배치) | **추가** | `osiris-stacks` 네임스페이스 신설 |
| `20` §3.1 / §3.4 | **스키마 델타 제안** | `:Organization`에 `dnsDomain`·`mailDomain`(둘 다 선택). 신규 라벨 `:CapabilityStackDecl`·`:Mailbox`·`:InboundMessage`, 관계 `HAS_MAILBOX`·`ORIGINATES_FROM`. **이 문서는 `20`을 고치지 않는다** — 소유자 확인 필요(§10) |
| 사용자 서술 | **부분 반박** | "외부 SMTP 릴레이면 송수신이 자가호스팅과 등가"는 프로토콜상 성립하지 않는다. 대신 키를 쪼개(S11) 모드 불가시성(S3)을 지키면서 비대칭을 표현한다(§4.2) |
