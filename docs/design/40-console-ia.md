# OSiris 관리 콘솔(WebUI) 정보구조 및 UX 설계

> 범위: 프론트엔드 화면 구조·인터랙션·실시간성·기술스택 권고, 그리고 이를 위해 백엔드가 제공해야 하는 API/이벤트 요구사항.
> 비범위: Agent Master 내부 구조, 온톨로지 스키마, k8s 토폴로지 — 다른 워커 담당. 이 문서는 해당 영역을 "요구사항"으로만 기술한다.
> 전제: 사용자는 대표(admin) 1인 + 소수 직원, 동시접속 10명 미만의 내부 도구. 엔터프라이즈급 권한체계·다국어·멀티테넌시는 의도적으로 배제한다.
> 배포 전제: OSiris는 기존 k8s 클러스터에 얹히는 앱이 아니라 **k8s 컨트롤 플레인 자체를 품고 배포되는 자족적 런타임**이다. 한 대에서 기동하면 컨트롤 플레인이 함께 뜨고, 워커 노드를 join시켜 확장한다. 클러스터 자체가 OSiris가 관리하는 대상이며 외부 인프라팀이 없다 — 그래서 운영(Ops) 화면은 에이전트 운영뿐 아니라 클러스터/노드 운영까지, 대표(비전문가) 눈높이로 다룬다(5절 참조).

- Notifications(#9)는 별도 페이지가 아니라 전역 헤더의 드롭다운 패널로, Approvals/Work/My Tasks로의 딥링크 허브 역할만 한다.

### 0. 로그인 / 등록 (Sign in) `[2026-07-27 신설]`

**목적**: 인증되지 않은 모든 진입의 도착점. 설계 근거·보안 성질은 전부 `60-identity-authn.md`가 소유하며, 여기서는 화면 요구만 적는다.

**세 모드** (탭이 아니라 **상태에 따라 하나만 보인다** — 선택지를 늘리면 사람이 무엇을 붙여넣어야 하는지 헷갈린다):

| 상태 | 보이는 것 |
|---|---|
| 조직 생성 **전**(`currentOrgRevision == 0`) | **마스터 키(master key) 입력** 하나만. **`[2026-07-27 갱신 — 명칭 재정의]`** 값의 출처(`osiris-up`이 터미널에 1회 출력, 재조회는 `bin/show-master-key.sh`)를 화면이 직접 설명한다 — **현행 `TokenEntryScreen.tsx`의 출처 설명·재조회 안내는 그대로 유지**하고(§95가 감독 피드백으로 만든 것), 명칭만 바꾸고 두 문장을 더한다(아래) |
| 조직 생성 **후** | **이메일 + 비밀번호** 기본. 그 아래 보조 링크 「등록/복구 티켓이 있어요」 |
| 티켓 상환 | 티켓 + 새 비밀번호(확인 포함). 성공하면 곧바로 로그인된 상태로 진입 |

**`[2026-07-27 신설]` 마스터 키 화면 문구 — 무엇을 지키고 무엇을 바꾸는가** (근거: `60-identity-authn.md` §4.0.1):

| | |
|---|---|
| **지킨다** | ① *"이 값은 **사람이 정하는 것이 아니라** 설치 시 `osiris-api`가 자동 생성한 값입니다"* — 출처 설명. ② *"최초 설치 시 `./osiris-up` 터미널에 한 번 출력되었습니다 — 놓쳤거나 다시 봐야 하면 서버에서 `bin/show-master-key.sh`를 실행하세요"* — 획득 경로 |
| **바꾼다 ①** | 명칭: "온보딩 관리 설정 토큰" → **"마스터 키(master key)"**. 입력 라벨·placeholder·파일 경로(`state/creds/admin/master_key`)·스크립트명 전부 |
| **바꾼다 ②** | **다음에 무슨 일이 일어나는지를 화면이 말한다** — 현행 문구는 "세션을 시작"에서 끝나 이 값이 일회성 관문처럼 읽힌다. 추가: *"마스터 키로 로그인하면 조직을 만들고, 그 다음 **본인의 비밀번호를 설정**하게 됩니다. 비밀번호를 설정하는 순간 이 마스터 키는 **영구히 폐기**됩니다."* |
| **바꾼다 ③** | 마지막 줄 *"교환 직후 폐기됩니다"*는 브라우저 측 사실만 말해 오해를 부른다 → *"이 값은 브라우저에 저장되지 않으며, 서버에서도 사용 즉시 새 값으로 회전됩니다."* |

**요구 사항**:
- 실패 응답은 원인을 구분하지 않는다(계정 없음/비밀번호 틀림/티켓 만료 전부 같은 문구) — 서버가 이미 그렇게 응답한다.
- 백오프로 지연될 때는 **잠긴 것이 아니라 느려진 것**임을 문구로 구분해 보여준다(`60-identity-authn.md` H15 — 이 시스템에는 계정 잠금이 없다).
- 토큰·비밀번호·티켓 어느 것도 `localStorage`/`sessionStorage`/URL에 **절대 저장하지 않는다**(현행 규칙 유지, Playwright 실측으로 고정된 조건 — `IMPLEMENTATION-NOTES.md` §89).
- 세션 만료(12h) 또는 401 발생 시 어떤 화면에서든 이 화면으로 복귀한다(현행 `authEvents` 전역 pub-sub 그대로).

### 1. Admin Chat

**목적**: 대표가 자연어로 지시하면 Master가 응답·WBS 생성·배정안을 제시하고, 대표가 그 자리에서 구조를 조작(수정/재배정/승인)한다. 채팅과 구조화 객체가 한 화면에서 공존해야 하므로, "대화 로그 안에 인터랙티브 카드가 인라인으로 렌더링"되는 방식을 채택한다(마치 채팅 안에 리치 카드가 뜨는 패턴 — 챗봇의 버튼/카드 UI와 동일 계열이나, 카드 내부가 트리 구조를 갖는 점이 다름).

**핵심 설계 결정**: 채팅 메시지 타입을 두 종류로 나눈다.
- `text` 메시지: 순수 대화
- `artifact` 메시지: Master가 만든 **WBS 초안 카드**(구조화 객체). 이 카드는 채팅 스트림에 얹혀 있지만 그 자체로 트리 편집 위젯이다.

WBS 카드 내부 상호작용:
- 각 태스크 행: 펼침/접힘, 담당자 배지(사람 아이콘 or 에이전트 아이콘 + 이름), "왜 이 사람인가" 설명 아이콘(ⓘ, 클릭 시 규칙 근거 팝오버 — C절 참조)
- 담당자 배지를 클릭 → 드롭다운으로 같은 capability를 가진 다른 후보로 즉시 재배정 가능(대표의 override는 채팅 안에서 완결)
- 태스크 텍스트/기한 인라인 편집(클릭하면 그 줄만 편집 모드)
- 태스크 추가/삭제(트리 내 우클릭 또는 행 끝 `+`/`⋯` 메뉴)
- 카드 하단 고정 액션바: `[전체 승인 및 실행]` `[일부만 승인]` `[다시 짜줘 — 코멘트]`
- "다시 짜줘"를 누르면 카드는 잠기고(재생성 중 표시), 대표가 남긴 코멘트가 다음 채팅 메시지로 이어져 Master가 새 카드를 만든다(이전 카드는 대화 히스토리에 "폐기됨" 상태로 남아 되돌아볼 수 있음 — audit trail).
- 승인 후 카드는 "실행 중" 상태로 전환되고, 그 이후로는 진행률 바 + 완료 태스크 체크가 실시간으로 그 카드 위에서 업데이트된다(대표가 Work 화면으로 옮겨가지 않고 채팅에서 진행을 지켜볼 수 있음). 카드 우상단 `[Work 보드에서 열기]` 링크로 전체 화면 이동 가능.

### 5. 운영 (Ops)

**전제 정정 반영**: OSiris는 기존 k8s 클러스터 위에 얹히는 앱이 아니라 **k8s 컨트롤 플레인 자체를 품고 배포되는 자족적 런타임**이다. 한 대에서 기동하면 컨트롤 플레인이 함께 뜨고, 워커 노드를 join시켜 확장한다. 즉 클러스터 자체가 OSiris가 관리하는 대상이고 별도 인프라팀이 없다 — 그래서 Ops 화면은 "에이전트 운영"뿐 아니라 **"이 조직이 돌아가는 하드웨어/클러스터 운영"까지** 대표(비전문가) 눈높이로 다뤄야 한다. kubectl 대시보드를 복제하지 않고, 전부 "직원·좌석·사무실" 은유로 번역한다.

**목적**: 에이전트 헬스/재시작/로그·트랜스크립트/비용(LLM 토큰 사용량) 대시보드 + 클러스터/노드(하드웨어 용량과 확장) 관리. dataviz 원칙 적용: 비용 추이는 단일축 시계열(더블축 금지), 헬스는 상태색 전용 트랙, 카테고리(팀별/에이전트별) 비교는 고정 순서의 카테고리 팔레트.

Ops는 화면 상단 탭으로 두 영역을 나눈다: **[에이전트 헬스/비용]** ↔ **[클러스터/노드]**. 같은 사이드바 진입점(🖥️ Ops) 아래 탭 전환이며 별도 사이드바 항목을 늘리지 않는다(과잉설계 금지 원칙).

**주요 요소 — 에이전트 헬스/비용 탭**:
- 상단: 전체 헬스 요약 스탯 타일(가동 N / 오류 N / 재시작 지난24h N)
- 좌: 에이전트 리스트(상태, 최근 재시작, 리소스 사용률)
- 중앙: 선택 에이전트의 실시간 로그 tail (스트리밍)
- 우: 비용 대시보드 — 팀별 토큰 사용량 시계열(단일 y축, 팀은 고정 카테고리 색), 일별 합계 스파크라인, 이번달 예산 대비 소진율(단일 진행바, 임계치 초과 시에만 warning/critical로 전환 — 평상시엔 중립색)

**주요 요소 — 클러스터/노드 탭** (신규):
- **최상위 경보 배너**: 컨트롤 플레인 자체의 건강 상태를 화면 맨 위 고정 배너로 표시(정상일 땐 조용히 접힘, 문제 시 화면 전체 폭으로 노출). 컨트롤 플레인이 죽으면 조직 전체(에이전트 배정·승인·온보딩 전부)가 멈추므로, 이는 개별 에이전트 오류보다 **한 단계 위의 경보 등급**으로 취급 — 색상은 status 팔레트의 critical을 그대로 쓰되 다른 어떤 알림보다도 시각적 우선순위(화면 최상단 고정, 알림센터에서도 항상 첫 줄)를 준다.
- **노드 목록**: 물리/가상 서버 단위 카드. 상태(정상/압박/오프라인)는 Org 화면과 동일한 상태색 이중 인코딩 규칙 재사용. 각 노드 카드에 그 노드에 얹힌 에이전트(Pod) 아바타 목록을 작게 나열 — "이 서버에 누가 살고 있는지"를 Org 화면과 시각적으로 연결.
- **좌석(seat) 환산 여유 용량**: CPU/메모리 잔여를 그대로(코어 수, GiB) 보여주는 대신, "이 정도면 개발자 에이전트 몇 명을 더 앉힐 수 있는가"로 환산한 **좌석 수 스탯 타일**을 주 지표로 노출. 원 수치(코어/GiB)는 보조 텍스트로 작게 병기(투명성 유지, 은유가 유일한 정보가 되지 않게).
- **노드 추가(join) 플로우**: `[+ 노드 추가]` 버튼 → 모달에서 join 토큰/커맨드를 콘솔이 발급 → 대표가 이 커맨드를 새 서버에 붙여넣어 실행하도록 안내(복사 버튼 + 만료 카운트다운) → 노드가 join하면 목록에 자동 등장하고 "가입 중 → 준비완료" 상태 전이를 실시간으로 보여준다.
- **노드 격리/드레인**: 노드 카드의 `[⋯]` 메뉴에서 "이 노드 비우기(drain)"를 지원 — 물리 서버를 내릴 때 그 위 에이전트를 다른 노드로 안전 이주.

**ASCII 와이어프레임**

```
┌─────────────────────────────────────────────────────────────────────────┐
│ OSiris  │ 🖥️ Ops   [에이전트 헬스/비용] [클러스터/노드]      🔔3  👤대표  │
├─────────┼─────────────────────────────────────────────────────────────────┤
```

#### 5-A. 「기계 주체(machine principal)」 섹션 `[2026-07-27 신설]`

**노출 조건**: `org.admin`. 설계 근거는 전부 `60-identity-authn.md` §19가 소유하며 여기서는 화면 요구만 적는다.

**왜 별도 화면이 아니라 Ops의 한 섹션인가**: 기계 주체는 **조직 구성원이 아니라 운영 자산**이다(§19의 MP4 — 조직도·배정·역량 어디에도 나타나지 않는다). People & Roles(#10)에 두면 "이것도 일종의 계정"이라는 잘못된 심상을 준다.

```
┌ 기계 주체 (검증·자동화 전용, 읽기 전용)                    [+ 발급] ┐
│ ⚠ 활성 2개 — 이 목록이 비어 있지 않은 동안 이 카드는 항상 보입니다  │
│                                                                     │
│  이름           클래스     스코프              만료      마지막 사용  │
│  ci-verify      org        onboarding, ops    D-24     3분 전  [⋯]  │
│  bootstrap-tmp  bootstrap  onboarding, ops    D-0 4h    —      [⋯]  │
│    └ ⓘ 조직 수립 + 관리자 비밀번호 설정과 동시에 자동 폐기됩니다      │
└─────────────────────────────────────────────────────────────────────┘
  [⋯] → 「회전」(새 값 1회 표시) · 「즉시 폐기」
```

**요구 사항**:
- **발급 모달**: 이름 · 스코프(**`org.read.*` 코드 체크박스만 — 다른 코드는 목록에 존재하지 않는다**) · TTL(기본 30일, 최대 90일). 저장 후 **평문 토큰을 딱 한 번** 표시하고 「복사」만 제공한다. **재조회 경로를 만들지 않는다** — 잃어버리면 회전한다.
- **접을 수는 있어도 감출 수 없다**(MP6). 활성 주체가 1개 이상이면 Ops 진입 시 항상 렌더된다.
- **리보크는 최대 60초 지연될 수 있음**을 확인 모달이 알린다(§7.4 양성 캐시).
- 발급·회전·폐기·**최초 사용**은 알림 센터(#9)에도 뜬다.
- `bootstrap` 클래스 행은 **발급 버튼에서 만들 수 없다** — 조직 생성 전 마스터 키 세션에서만 생기며, 이 화면에서는 **관측·폐기만** 가능하다.

#### 6.1 대화 상대는 「온보딩 컨설턴트」이고, 확정 버튼은 사람의 것이다 `[2026-07-28]`

`30-onboarding-provisioning.md` §3.4(O15)가 1단계 온보딩의 대화 주체를 **온보딩
컨설턴트**로 명명하고 그 권한에서 `POST /onboarding/commit`을 제거했다. 이 화면에
그대로 반영해야 하는 것 세 가지:

1. **화자 라벨을 `Master`가 아니라 `컨설턴트`로 표기한다.** 위 와이어프레임의
   `Master)`는 1회차 온보딩에서 **사실과 다르다** — 그 시점에 `agent-master`는 그래프에도
   런타임에도 존재하지 않는다(§1.1의 순환 문제 그 자체). 2회차 이후 재온보딩에서는
   진짜 Master일 수 있으므로, 라벨은 **서버가 내려주는 값**이어야 하고 화면이 추측하면
   안 된다(G10: 규칙을 프론트에 하드코딩하지 않는다).

2. **확정 액션의 문구가 주체를 드러내야 한다.** 컨설턴트의 산출물은 **제안서**이고,
   조직을 확정하는 것은 사람이다. 화면 #10이 `[+ 사람 추가]`를 **「조직에 추가하고
   커밋」**으로 바꿔 무게를 드러낸 것과 같은 이유로(위 §A-8), 여기서도 「다음」이 아니라
   **「검토했고 조직으로 확정」** 류의 문구를 쓴다. 이 버튼이 곧 §3.4.3의 커밋 호출자
   (1회차: master key 세션 / 2회차 이후: `org.admin` 사람 세션)다.

3. **컨설턴트가 못 하는 일을 UI가 할 수 있는 것처럼 보이면 안 된다.** 대화 중
   "지금 바로 반영해줘"라고 말해도 컨설턴트는 커밋할 수 없다 — 그 경우 컨설턴트는
   초안 카드를 갱신하고 **확정 버튼을 가리키는** 것으로 답해야 한다. 이것을 안내
   문구로만 두면 LLM이 지키지 못할 수 있으므로, **구조적 보장은 스코프**이고
   (`commit`을 부를 수단 자체가 없다) UI 문구는 그 위의 친절함이다.

#### 6.2 이 화면은 스트리밍에 의존한다 — 0-6이 그 전제를 검증한다 `[2026-07-28 O16]`

위 §D의 표는 대화 스트림을 *"매우 높음(타이핑 체감)"* 요구로 분류하고 **SSE**로
확정했다. 컨설턴트 대화가 1단계 온보딩의 **유일한 경로**가 되었으므로, 그 전제가
깨지면 이 화면은 빈 화면이 된다. `30-onboarding-provisioning.md`가 0단계 완료조건에
**0-6(스트리밍 패스스루 검증)**을 추가한 이유가 이것이다.

**`[2026-07-28 실측 완료]` 이 화면의 전제는 검증되었다.** `30` §1.0.3.2가 omniroute와
`osiris-gw` 모두 SSE를 버퍼링하지 않음을 실측으로 확인했다(프레임이 20초에 걸쳐 분산
도착, 하트비트 프레임 관측, `Content-Type: text/event-stream`). 따라서 타이핑 인디케이터
요구를 내려놓는 (a)안은 **불필요하다.** 남은 미검증 구간은 "프로바이더 → omniroute"
한 홉뿐이며, 그것은 0-6이 설치 시 자동으로 확인한다(`30` §1.0.3.3).

### 10. 사람·역할 관리 (People & Roles) `[2026-07-27 신설]`

**목적**: 사람을 추가하고, **조직 역할**(관리자/매니저/구성원)을 부여·변경하고, 로그인 수단(등록 티켓)을 발급하고, 퇴사자를 비활성화한다. 설계 근거·위임 규칙·권한 상승 분석은 전부 `60-identity-authn.md` §20~§21이 소유하며, 여기서는 화면 요구만 적는다.

**노출 조건**: `org.manage.people` 또는 `org.manage.roles`(둘 다 없으면 사이드바에 항목 자체가 없다).

**왜 기존 화면에 넣지 않는가**: #6 Onboarding은 **대화형 마법사**이고(`30-onboarding-provisioning.md` §1.0.2가 폼과 대화를 명시적으로 갈랐다), #7 Ontology는 **범용 그래프 편집**이라 위임 규칙을 표현할 자리가 없으며, #5 Ops는 **런타임 관측**이다. 사람·역할·계정 상태는 셋 중 어디도 아니다.

**★ 이 화면의 핵심 요구 — 버튼의 유무를 프론트가 판단하지 않는다.**
"이 사람의 역할을 바꿀 수 있는가 / 티켓을 발급할 수 있는가"는 `60-identity-authn.md` §21의 위임 규칙(DG1~DG5)이 결정한다. **그 규칙을 프론트가 재구현하면 인가 판정이 두 곳에 존재하게 되고 그 자체가 결함이다.** 그래서 사람 목록 응답의 **각 행에 백엔드가 `allowedActions` 배열을 계산해 싣고**, 콘솔은 그 배열에 없는 액션을 **아예 그리지 않는다.** 좌석 환산(G10)·사이드바(`consoleSurfaces`)와 같은 원칙의 **행 단위 적용**이다.

```
┌─────────────────────────────────────────────────────────────────────────┐
│ OSiris  │ 👥 People & Roles                              🔔3  👤대표     │
├─────────┼─────────────────────────────────────────────────────────────────┤
│ …사이드 │  [+ 사람 추가]                      검색 [        ]  ☐ 비활성 포함│
│  바     │ ─────────────────────────────────────────────────────────────  │
│         │  이름     이메일             조직역할   팀/직무        계정상태   │
│         │  대표     ceo@…              관리자     —             ✓ 활성    │
│         │    └ (본인 — 역할 변경 불가)                          ⓘ DG3     │
│         │  김지혜   jihye@…            매니저     경영관리       ✓ 활성 [⋯]│
│         │  박민수   minsu@…            구성원     alpha/개발     ⏳ 티켓   │
│         │    └ 등록 티켓 미상환 (D-5)                              [⋯]    │
│         │  이수진   sujin@…            —          마케팅         ⚠ 미설정 │
│         │    └ 로그인 수단 없음 — 티켓을 발급하세요                [⋯]    │
└─────────┴─────────────────────────────────────────────────────────────────┘
  [⋯] → 「조직 역할 변경」 · 「등록 티켓 발급」 · 「세션 전체 종료」 · 「비활성화」
        ※ 각 항목은 서버가 그 행에 대해 allowedActions 에 실어 보낸 것만 나타난다
```

**요구 사항**:

1. **계정 상태 3종을 구분해 보여준다** — `✓ 활성`(자격증명 보유) / `⏳ 티켓`(미상환 등록 티켓 있음, 남은 일수) / `⚠ 미설정`(로그인 수단 없음). **이 정보는 그래프에 없다** — `GET /people/{id}/auth-state`가 원천이다(`60-identity-authn.md` §2.7-3).
2. **등록 티켓 발급 모달**: 평문 티켓을 **딱 한 번** 표시 + 「복사」. *"이 값은 다시 볼 수 없습니다. 본인에게 직접 전달하세요(대역외)"*를 함께 표시(H12 — 메일 발송 경로를 전제하지 않는다). 알림 어댑터가 구성되어 있고 그 사람의 `notifyChannels`에 채널이 있으면 「이 채널로 보내기」가 **추가로** 나타난다(선택 기능, 없어도 정상).
3. **조직 역할 변경 모달**: 선택 가능한 역할은 **서버가 계산해 내려준 목록만**(DG1의 부여 상한이 이미 적용된 결과). 매니저의 화면에는 "관리자"가 **선택지로 존재하지 않는다** — 눌렀다가 403을 받는 것이 아니라 애초에 없다.
4. **거부는 이유와 함께**: 서버가 403을 반환할 때 규칙 식별자(DG1~DG5)와 한 줄 설명을 함께 주고, 콘솔은 그것을 그대로 보여준다. *"권한이 없습니다"*만 띄우면 사람이 무엇을 잘못했는지 모른다.
5. **관리자를 대상으로 하는 액션은 확인 다이얼로그 + 경고**: *"이 작업은 다른 관리자 전원에게 즉시 통지됩니다"*(DG5). 실제로 그렇게 동작하므로 놀라지 않게 미리 말한다.
6. **마지막 관리자 보호**: 마지막 관리자를 강등·비활성화하려 하면 409와 함께 *"조직에 관리자가 최소 1명 있어야 합니다. 먼저 다른 사람을 관리자로 지정하세요"* + 그 화면으로의 딥링크(DG4).
7. **역할 이력**: 사람 상세에 **"이 사람의 조직 역할 변경 이력"**(언제부터 언제까지 무슨 역할)을 보여준다 — `:Membership`의 `validFrom`/`validTo`/`createdAtRevision`이 이미 그 값을 갖고 있다(`60-identity-authn.md` §20.2-2가 이 표현을 택한 이유가 정확히 이것이다).
8. **`[+ 사람 추가]`는 `:OrgRevision`을 올린다** — 조직 의도 변경이므로(C8/H32). 저장 버튼 문구를 「추가」가 아니라 **「조직에 추가하고 커밋」**으로 두어 그 무게를 드러낸다. 반면 티켓 발급은 리비전을 올리지 않으므로 즉시 반영된다.

## B. 핵심 인터랙션 플로우 3개 (화면 전환 단위)

### 플로우 1 — "다음 달 예시 앱 신규 광고 캠페인 준비해"

1. **Admin Chat**: 대표가 텍스트 입력. 전송 즉시 스트리밍으로 Master 응답 시작(타이핑 인디케이터).
2. **Admin Chat (인라인 카드 생성)**: Master가 WBS 초안을 `artifact` 메시지로 렌더링(위 와이어프레임). 각 리프에 배정된 담당자와 ⓘ 근거 아이콘 표시.
3. **Admin Chat (수정)**: 대표가 3번 태스크 담당자 배지를 클릭 → 후보 드롭다운(같은 capability 보유자만 노출, 근거와 함께) → "대표(본인)"으로 override. 카드가 즉시 갱신(낙관적 UI, 실패 시 롤백).
4. **Admin Chat (승인)**: `[전체 승인 및 실행]` 클릭 → 확인 다이얼로그 없이 즉시 실행 상태로 전환(승인 자체는 가벼운 액션이므로) — 단, 카드 내 태스크 중 외부영향 액션(예: "매체 집행 설정" 실제 광고 계정 조작)이 있는 태스크는 실행 시점에 자동으로 **Approvals 큐**에 별도로 쌓인다(이건 5번 태스크가 실제 집행 시점에 발생, 지금이 아님).
5. **화면 전환 (선택적)**: 대표가 카드 우상단 `[Work 보드에서 열기]` 클릭 → **Work** 화면으로 이동, 동일 WBS가 트리 형태로 전체화면 표시. 이후 진척은 Work에서도, Admin Chat 카드에서도 동시에 업데이트(같은 서버 상태를 구독).
6. **진행 중**: 각 리프 태스크가 완료될 때마다 Admin Chat 카드와 Work 트리의 진행률 바가 실시간 갱신. 담당 에이전트가 오류를 내면 해당 리프에 ● 오류 배지가 뜨고 알림 센터에 항목 추가.
7. **완료보고**: 마지막 태스크(6. 대표 최종 검수)가 완료되면 Master가 Admin Chat에 요약 메시지(`text`)로 완료보고("캠페인 준비 완료, 소재 3종/예산 120만원/집행 시작 8/18") 전송. 카드 상태가 "완료"로 고정되고 Work 트리에서도 100% 마감 처리.

### 플로우 2 — 개발자 에이전트의 코드 커밋 → 승인

1. **(백그라운드)** 개발자A 에이전트가 태스크를 수행하며 브랜치에 커밋 준비를 마침 → 백엔드가 승인 요청 이벤트 발행.
2. **알림 센터**: 헤더 종 아이콘에 뱃지 증가, 드롭다운에 "개발자A: 결제모듈 리팩터 커밋 승인 요청" 항목 표시.
3. **Approvals**: 대표가 알림 클릭 → Approvals 화면으로 이동, 해당 항목이 선택된 상태로 열림. 좌측 큐, 우측 diff 상세 자동 로드.
4. **검토**: 대표가 diff·CI 결과·연관 태스크 맥락(어느 WBS 항목에서 나온 커밋인지 링크)을 확인.
5. **분기**:
   - **승인**: `[✓ 승인]` → 백엔드가 실제 커밋/머지 실행, 큐에서 항목 제거, Work 보드의 해당 태스크가 "완료"로 전환, Org 화면의 개발자A 노드가 "가동→유휴"로 전환.
   - **반려**: `[✗ 반려]` → 코멘트 필수 입력 → 태스크가 담당 에이전트에게 "반려됨" 상태로 돌아가고 Admin Chat에 Master의 반려 사유 전달 메시지가 생성됨.
   - **수정요청**: `[↺ 수정요청]` → 코멘트와 함께 원 에이전트 큐로 되돌림, 승인 큐에서는 제거되고 재작업 후 다시 큐에 들어옴(새 승인요청 ID로).

### 플로우 3 — 사람 직원에게 물리 업무 배정 → 완료보고 → 검증

1. **(백그라운드)** Master가 WBS 분해 중 "네트워크 구성" 등 물리 업무를 capability 매칭으로 총무 담당자(사람)에게 배정.
2. **알림(외부채널 + 콘솔)**: 해당 직원에게 알림(콘솔 알림 센터 + 필요시 외부 메신저 연동, 이 문서 범위 밖이나 알림 이벤트는 동일 소스). 직원이 콘솔 로그인 시 사이드바에 **My Tasks** 뱃지.
3. **My Tasks**: 직원이 카드 클릭 → 상세(체크리스트, 상위 캠페인/프로젝트 맥락, 마감) 확인. 하위 체크리스트 항목을 하나씩 체크(PC #1 셋팅 완료 등).
4. **완료보고**: 모든 하위 항목 체크 후 `[완료보고]` 클릭 → 메모/사진 첨부 모달 → 제출.
5. **검증대기 전환**: 태스크 상태가 "검증대기"로 바뀜. 대표(또는 해당 팀장 에이전트)에게 알림 발생.
6. **Work 또는 Admin Chat에서 검증**: 대표가 Work 보드에서 해당 리프를 열어 첨부 사진/메모 확인 → `[검증 완료]` 또는 `[반려(재작업 요청)]`. 검증 완료 시 상위 WBS 진행률이 롤업 갱신.

## C. 설명가능성(Explainability) 설계

배정이 LLM의 즉흥 판단이 아니라 **온톨로지 capability 매칭에 의한 결정적 계산**이라는 사실을 UI가 신뢰의 근거로 명시적으로 드러내야 한다.

- **ⓘ 배지(모든 배정 표시 지점 공통 컴포넌트)**: WBS 카드의 담당자 배지, Org 노드 상세 패널, Work 트리의 담당자 열에 동일한 ⓘ 아이콘을 둔다. 클릭(또는 hover) 시 팝오버로 다음을 보여준다:
  ```
  ┌ 배정 근거 ─────────────────────────────┐
  │ 태스크 요구 capability: 매체집행, 리포팅  │
  │ 후보:                                    │
  │  ✓ 마케팅-AI   보유: 매체집행,리포팅,카피 │ ← 선택됨
  │    경영관리    보유: 리포팅               │  (매체집행 없음 → 제외)
  │    개발자A     보유: 없음                 │  (제외)
  │ 규칙: capability 전량일치 우선, 동률 시   │
  │       현재 부하(active task 수) 최소 선택│
  └───────────────────────────────────────┘
  ```
  이 팝오버는 "이 사람이 됐다"가 아니라 "이 규칙과 이 후보 비교 때문에 이 사람이 됐다"를 항상 후보 비교표 형태로 보여준다 — 단일 이유 텍스트가 아니라 **탈락자와 탈락 사유까지** 포함하는 것이 핵심(왜 다른 사람이 아닌지가 신뢰를 만든다).
- **override 이력 표시**: 대표가 Admin Chat에서 배정을 수동 override하면, 그 태스크의 ⓘ에는 "규칙 배정: 경영관리 → 대표 override(7/26, 대표 직접 지정, 사유: 없음)"처럼 규칙값과 override값을 모두 남긴다. 규칙 계산 결과를 지우지 않고 override를 그 위에 얹힌 레이어로 시각화 — 나중에 "원래 규칙대로였으면 누구였을지"를 항상 되짚을 수 있게 한다.
- **일관성**: 이 팝오버 컴포넌트는 화면마다 새로 디자인하지 않고 하나의 공용 컴포넌트(`AssignmentRationalePopover`)로 Admin Chat/Org/Work 3곳에서 재사용 — 사용자가 한 번 배우면 어디서나 같은 방식으로 "왜"를 캘 수 있다.

## D. 실시간성 요구사항

| 화면/데이터 | 실시간성 요구 | 권장 전송방식 | 근거 |
|---|---|---|---|
| Admin Chat 대화 스트림(토큰 단위 응답) | 매우 높음(타이핑 체감) | **SSE**(서버→클라 단방향 스트림) | LLM 응답은 서버가 생성하는 순간 순차 전송되는 단방향 스트림. 클라이언트가 서버로 실시간 데이터를 보낼 필요는 전송 시작 시점 1회 요청뿐이므로 양방향 소켓은 과함. |
| WBS 카드 진행률/상태 갱신 | 높음(수 초 지연 허용) | **SSE**(같은 채널 또는 별도 이벤트 스트림) | 서버 주도 이벤트 푸시. Admin Chat과 같은 커넥션 계열로 묶으면 인프라 단순화. |
| Ops 로그 tail | 매우 높음(로그는 라인 단위 즉시성 기대) | **SSE** | 로그도 본질적으로 append-only 단방향 스트림. WebSocket이 필요한 경우(클라이언트가 로그 레벨 필터를 서버에 실시간으로 재협상해야 하는 등 양방향 제어)가 아니면 SSE로 충분. |
| Org 노드 상태(가동/오류 등) | 중간(수 초~십수 초 지연 허용) | **SSE push**(경량 이벤트, payload는 노드ID+상태만) | 상태 변화는 드물게 발생하는 이벤트이므로 풀 그래프 재조회가 아니라 델타 이벤트 푸시가 맞음. 폴링도 기술적으론 가능하나(10초 간격) 대표가 오류를 "실시간으로 알아채야" 하는 요구(사람-응답대기, 오류 상태)가 있어 push가 더 적합. |
| 승인 큐 신규 항목 등장 | 높음(대표가 놓치면 병목) | **SSE + 알림 뱃지** | 승인 대기는 곧 조직 전체가 블록되는 지점이므로 지연 없이 알아야 함. |
| Work 보드 트리 전체 | 낮음~중간 | **초기 로드는 REST, 이후 SSE로 델타 패치** | 트리 전체를 매번 스트리밍할 필요 없음. 최초 전체 조회 후, 변경된 노드만 이벤트로 패치. |
| Ops 비용/리소스 대시보드(집계 통계) | 낮음 | **폴링(30~60초)** | 비용 집계는 배치성 데이터(토큰 사용량 합산)라 초 단위 정확도가 무의미. 폴링으로 충분하고 구현이 훨씬 단순. |
| 온톨로지 그래프 브라우징 | 낮음(사람이 직접 조회할 때만) | **REST 온디맨드(요청 시 조회)** | 상시 구독 대상이 아님. 편집 시에만 저장 요청. |
| My Tasks 리스트 | 중간 | **폴링(15~30초) 또는 방문 시 REST + 알림 이벤트로 트리거 재조회** | 사람 직원 화면은 상시 열려있지 않을 가능성이 높아, 상시 커넥션보다 알림 수신 시 재조회가 리소스 효율적. |
| **컨트롤 플레인 헬스** | **매우 높음(전 조직이 이 신호에 의존)** | **SSE push, 최우선 경보 채널** | 컨트롤 플레인이 죽으면 배정·승인·온보딩 등 모든 화면이 동시에 멈추므로, 다른 어떤 이벤트보다 지연 없이 도달해야 함. 게이트웨이 자체가 컨트롤 플레인에 얹혀 있을 수 있어(자족 런타임 특성), 게이트웨이-컨트롤플레인 동시 장애 시 SSE 자체가 끊기는 경우를 대비해 **콘솔이 SSE 연결 끊김을 그 자체로 "컨트롤 플레인 이상 의심" 신호로 해석**하는 별도 클라이언트 로직(연결 끊김 지속시간 임계치 초과 시 배너 자동 노출)이 필요 — 순수 서버 푸시만으로는 "서버가 죽어서 못 알리는" 케이스를 못 알리기 때문. |
| 노드 목록/상태(정상/압박/오프라인) | 중간(수 초~수십 초 지연 허용) | **SSE push**(노드ID+상태+용량 델타) | 하드웨어 장애·리소스 압박은 드물지만 놓치면 "직원을 더 못 뽑는" 상황을 대표가 모르고 배정을 계속 시도하게 되므로 push가 적합. |
| 노드 join 진행상황(토큰 발급 후 대기 중 → 완료) | 높음(모달 열어둔 동안 즉시 피드백 기대) | **SSE(모달 세션 한정 구독)** | 사용자가 화면을 보며 기다리는 짧은 트랜잭션이므로 폴링보다 push가 체감상 자연스러움. |

**결론**: 콘솔 전역 실시간 채널은 **SSE 하나**로 통일(단방향 서버 푸시가 요구의 대부분). WebSocket이 필요한 유일한 후보는 "대표가 스트리밍 중인 응답을 중간에 취소/개입"하는 시나리오 정도인데, 이는 SSE 스트림을 열어둔 채 별도의 짧은 REST POST(`/chat/{id}/cancel`)로 충분히 해결 가능하므로 WebSocket 도입 근거가 부족하다. 폴링은 순수 집계/저빈도 데이터(비용 대시보드, My Tasks)에 한정한다.

## E. 기술 스택 권고

**권고: React + TypeScript(Vite) SPA / 백엔드 API 게이트웨이는 경량 Node.js(또는 기존 백엔드 언어에 맞춤, HTTP+SSE만 얹으면 됨) / 실시간은 SSE 단일 채널 / 그래프 뷰는 경량 force-layout 라이브러리(예: 소규모 노드 수 전제) / 상태관리는 서버 상태 캐시 라이브러리(React Query류) + 채팅 스트림은 자체 리듀서**

이유 및 탈락 사유:

- **React SPA vs 서버렌더 프레임워크(Next.js 등 SSR)**: 이 콘솔은 SEO가 필요 없고, 동시접속 10명 미만의 내부 도구이며 화면 대부분이 로그인 후 지속 세션에서 실시간 스트림을 유지하는 대시보드형이다. SSR의 이점(초기 로드 SEO, 스트리밍 HTML)이 요구사항에 없고, 오히려 SSE 연결·클라이언트 상태 유지가 핵심인 앱에서는 순수 SPA가 구조가 단순하다. → **Next.js 탈락**: 추가 이점 대비 서버 인프라 복잡도(SSR 서버 유지, 캐싱 전략) 도입 근거 부족.
- **WebSocket 프레임워크(Socket.io 등) vs SSE**: D절에서 분석했듯 요구 트래픽이 거의 전부 서버→클라 단방향이다. SSE는 표준 HTTP 위에서 동작해 프록시/로드밸런서 설정이 단순하고, 브라우저 네이티브 `EventSource`로 재연결도 자동 처리된다. → **Socket.io/WebSocket 탈락**: 양방향 요구가 사실상 없는데 별도 프로토콜과 커넥션 관리 복잡도(스티키 세션, 별도 스케일링 고려)를 도입할 이유가 없음. k8s 위에서 다수 서버 인스턴스로 확장할 계획이 있다면 WebSocket은 스티키 세션이 필요해지지만 SSE는 HTTP 기반이라 이 문제가 훨씬 가볍다.
- **상태관리**: 화면 대부분이 "서버가 주는 상태를 보여주고 가끔 변형(mutate)"하는 패턴이므로, 서버 상태 캐시 라이브러리(TanStack Query류) + 로컬 UI 상태만 별도(Zustand 등 경량)로 충분. Redux류의 전역 상태 아키텍처는 이 규모(10명 미만, 화면 9개)에는 보일러플레이트 대비 이득이 없다. → **Redux 탈락**: 오버엔지니어링.
- **그래프 시각화(Org, Ontology)**: 조직 규모가 3~4계층·팀 4개·소수 직무이므로 노드 수가 애초에 작다(수십 개 미만). 본격 그래프 엔진(Cytoscape 대규모 그래프 최적화, WebGL 렌더러)은 불필요 — 트리형은 단순 CSS/flex 레이아웃, 온톨로지 자유그래프 뷰만 경량 force-layout으로 족하다. → **대형 그래프 전용 엔진(WebGL 기반) 탈락**: 노드 수 규모에 비해 과설계.
- **차트(비용/리소스 대시보드)**: dataviz 스킬 원칙에 따라 단일축 시계열·상태색 전용 트랙 등 단순한 마크 스펙만 필요하므로 경량 SVG 차트 라이브러리로 충분. 복잡한 BI 대시보드 프레임워크 도입 불필요.
- **백엔드/실시간 계층**: 이미 k8s + 그래프DB + 메시지버스가 있다는 전제이므로, 콘솔 전용으로 새 상태저장소를 만들지 않고 **API 게이트웨이 하나**(그래프DB/메시지버스를 대신 조회·구독해 REST+SSE로 정규화해 콘�트에 제공)만 얇게 둔다. 이 게이트웨이가 메시지버스를 구독해 SSE로 팬아웃하는 구조 — 버스에 콘솔이 직접 붙지 않게 하여 프론트가 버스 프로토콜에 종속되지 않도록 격리.

## F. 백엔드에 요구하는 API / 이벤트 목록 (요구사항 — 구현은 백엔드 워커 담당)

> 아래는 "콘솔이 동작하기 위해 백엔드가 반드시 노출해야 하는 계약"이다. 엔드포인트명·페이로드 스키마는 예시이며 확정 사양이 아니다.
>
> **경로 표기에 대한 주석(2026-07-27 추가, 이 문서 자신은 수정하지 않고 표기만 명확히 함)**: 아래 표의 경로(예: `GET /orgs/tree`)는 `osiris-api`가 실제로 라우팅하는 **내부 엔드포인트 식별자**이며 그대로 유지된다. `10-core-architecture.md` §2.9(I5 3차 수정)로 `osiris-gw`의 공개 경로 네임스페이스가 `/api/`에서 `/_api/`로 옮겨졌지만, 이건 **콘솔 클라이언트(브라우저)가 부르는 base URL**만의 문제다 — `osiris-gw`가 `/_api/*` 요청을 `/api/*`로 벗겨서 `osiris-api`에 그대로 전달하므로, 이 표의 경로들은 `osiris-api` 내부 구현 기준으로 **변경 없음**(`10-core-architecture.md`의 "다음 워커(콘솔)에게" 인계 사항과 일치). 콘솔 SPA를 구현하는 워커는 fetch/EventSource의 base URL을 `/_api`로 잡을 것 — 이 표의 경로 문자열 앞에 `/_api`를 붙인 것이 실제로 브라우저가 치는 URL이다(예: `GET /orgs/tree` → 브라우저는 `GET /_api/orgs/tree`).

| **`POST /machine-principals`** | 발급. 본문 `{name, permissions[], ttlDays}` — `permissions`는 `org.read.*`만 허용(그 외는 400). **평문 토큰이 이 응답에 딱 한 번** 실린다. 호출 가능 주체: `org.admin` 세션 **또는 조직 생성 전의 master key 세션**(§19.5). **기계 주체 자신은 절대 호출할 수 없다**(H27) |
| **`POST /machine-principals/{id}/rotate`** | 새 값 발급 + 구 값 즉시 무효. 평문은 응답에 1회 |
| **`DELETE /machine-principals/{id}`** | 즉시 폐기(최대 60초 지연 — 양성 캐시) |
| **`GET /whoami`** | **기계 주체 전용 자기조회** — `{kind:"machine", principalId, permissions, expiresAt}`. **`partyId` 필드가 응답 스키마에 아예 없다**(있으면 언젠가 누군가 채운다). 기계 주체는 `GET /me`를 부를 수 없다(403) |
| `GET /cluster/control-plane/health` | 컨트롤 플레인 자체의 건강 상태(정상/이상) — Ops 최상위 경보 배너의 데이터 소스 |
| `GET /cluster/nodes` | 노드 목록 — 상태(정상/압박/오프라인), 얹힌 에이전트 Pod 목록, CPU/메모리 원 수치 |
| `GET /cluster/nodes/{id}/capacity` | 노드(또는 전체) 여유 용량 — **좌석 환산값**(예: "개발자 에이전트 N명 더 수용 가능")을 원 수치와 함께 반환. 좌석 환산 로직(직무별 표준 리소스 프로파일 대비 계산)은 백엔드 책임, 콘솔은 결과값만 표시 |
| `POST /cluster/nodes/join-token` | 신규 노드 join용 토큰/커맨드 발급(만료시간 포함) |
| `POST /cluster/nodes/{id}/drain` | 노드 비우기(위 에이전트를 다른 노드로 안전 이주) |
| `DELETE /cluster/nodes/{id}` | 노드 제거(드레인 완료 후) |

### 백엔드에 요구하는 비-API 계약(설계 전제 요구사항)

- **배정 근거는 배정 시점에 함께 영속화**되어야 함(사후에 재계산해서 보여주는 것이 아니라, 그 시점의 후보 비교 스냅샷을 저장) — 조직이 나중에 바뀌어도 과거 배정의 "왜"가 그대로 재현되어야 설명가능성이 성립.
- **override는 규칙 계산 결과를 덮어쓰지 않고 별도 레이어로 저장** — `/assignments/{taskId}/rationale`이 "규칙값"과 "최종 override값"을 둘 다 반환해야 C절 UI가 가능.
- **승인 게이트 대상 액션 타입(커밋/발송/지출)마다 표준화된 미리보기 payload 스키마**가 필요 — 콘솔은 타입별 렌더러(diff viewer / 메시지 미리보기 / 금액+영수증 뷰)를 붙이므로, 백엔드가 타입 판별 필드(`approvalType`)와 그에 따른 고정 payload 구조를 계약해야 함.
- **사람 노드의 "응답대기" 상태를 백엔드가 1급 상태로 관리**해야 함(에이전트 오류와 동일한 우선순위 알림 경로를 타야 하므로, 사람 지연도 조직 전체 헬스 신호로 취급).
- **SSE 재연결 시 유실 이벤트 복구**를 위해 이벤트에 순번(`seq`)/타임스탬프를 부여하고, 재연결 시 `Last-Event-ID` 기반 이후 이벤트 재전송을 게이트웨이(또는 그 하위 버스)가 지원해야 함.
- **화면 가시성(사이드바 항목·화면 게이팅)은 백엔드가 계산해서 값으로 내려줘야 함** `[2026-07-27 신설]` — 콘솔은 `GET /me`의 `consoleSurfaces` 배열을 그대로 렌더하고, "누가 무엇을 볼 수 있는가"의 규칙을 프론트에 재구현하지 않는다. 파생 규칙(어떤 기존 사실에서 어떤 화면이 나오는가)은 `60-identity-authn.md` §3.3이 소유하며, 권한·멤버십이 바뀌면 프론트 배포 없이 값이 따라 바뀌어야 한다. 좌석 환산 요구와 동일한 원칙(`10-core-architecture.md` G10).
- **대상별 허용 액션도 백엔드가 계산해서 값으로 내려줘야 함** `[2026-07-27 2차 신설]` — 화면 가시성(위 항목)의 **행 단위 확장**이다. `GET /people`의 각 행에 `allowedActions` 배열을 실어, "이 사람의 역할을 바꿀 수 있는가 / 티켓을 발급할 수 있는가 / 비활성화할 수 있는가"를 서버가 판정한다. 콘솔은 그 배열에 없는 버튼을 **그리지 않는다**. 이 규칙(위임 규칙 DG1~DG5, `60-identity-authn.md` §21)을 프론트가 재구현하면 **인가 판정이 두 곳에 존재**하게 되고, 그 순간 둘이 어긋나는 것을 아무도 잡을 수 없다. 마찬가지로 `GET /roles/org`는 **부여 가능한 역할만** 반환한다 — 매니저의 화면에 "관리자"가 선택지로 나타났다가 403을 받는 일이 없어야 한다.
- **기계 주체는 사람이 아니다** `[2026-07-27 2차 신설]` — 비대화형 호출자(CI·검증 스크립트)는 `Authorization: Bearer osm_…`로 인증하며 **쿠키를 받지 않고, 세션을 만들지 않고, `:Party`를 갖지 않고, 어떤 mutating 엔드포인트도 부를 수 없다**(`60-identity-authn.md` §19). 콘솔은 이들을 조직도(#2)·People & Roles(#10)에 **절대 표시하지 않으며**, Ops(#5-A)의 운영 자산으로만 다룬다.
- **로그인한 사람은 반드시 `:Party` 신원을 가져야 함** `[2026-07-27 신설]` — 모든 변경 요청의 행위자는 세션에서만 파생되며(요청 본문/쿼리에서 읽지 않는다), `:Approval.DECIDED_BY`·`:AssignmentOverride.BY`·`:OrgRevision.byPartyId`가 그 값으로 채워진다. 콘솔의 "누가 승인했는가"·"누가 override했는가" 표시는 이 계약 위에서만 성립한다(`60-identity-authn.md` H4/H19/§6).
- **좌석 환산 로직은 백엔드가 계산해서 값으로 내려줘야 함**(콘솔에서 CPU/메모리 원 수치를 직무별 리소스 프로파일과 대조해 재계산하지 않는다) — 직무별 표준 리소스 프로파일 정의·환산 공식은 백엔드/온톨로지 워커의 책임이며, 콘솔은 결과 좌석 수만 표시. 프로파일이 바뀌면(예: 개발자 에이전트 컨테이너 스펙 변경) 좌석 수 값도 자동으로 갱신되어야 하므로 정적 상수로 프론트에 하드코딩하지 않는다.
- **게이트웨이와 컨트롤 플레인의 동시 장애 가능성을 백엔드 배포 설계가 인지해야 함** — 자족적 런타임 특성상 콘솔이 통신하는 게이트웨이 자체가 컨트롤 플레인 위에서 돌 수 있다. 이 경우 "컨트롤 플레인 이상"을 알려야 할 이벤트 채널 자체가 끊기는 역설이 발생하므로, 최소한 게이트웨이만은 컨트롤 플레인과 장애 도메인을 분리(별도 프로세스/헬스체크 경로)하거나, 콘솔이 SSE 연결 자체의 두절을 경보로 해석할 수 있도록 하트비트 이벤트(`cluster.heartbeat`, 예: 10초 간격)를 상시 발행해야 함 — 하트비트 부재가 곧 신호가 되도록.
